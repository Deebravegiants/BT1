### Title
Client-controlled `MessageID` overwrite causes cross-user response confusion in legacy WebAPI trigger handler - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
The bug report describes an unvalidated `orderId` that can be reused across purchases, causing an off-chain consumer of the emitted event to conflate unrelated transactions. The closest reachable analog in the chainlink gateway is `handler.HandleLegacyUserMessage`, which stores a pending user callback keyed only by the client-supplied `msg.Body.MessageID`, with no check for an existing/in-flight entry with the same ID — unlike the newer v2 trigger handler, which explicitly rejects duplicate request IDs.

### Finding Description
In `core/services/gateway/handlers/capabilities/handler.go`, `HandleLegacyUserMessage` unconditionally overwrites the `savedCallbacks` map with the caller-supplied `MessageID`: [1](#0-0) 

`MessageID` is part of `api.MessageBody`, is chosen by the message sender, and is only length/format validated (non-empty, ≤128 bytes, no trailing null byte) in `Message.Validate`: [2](#0-1) 

There is no uniqueness constraint on `MessageID` and no ownership binding between the stored callback and the identity of the request that created it — dispatch to a saved callback later happens purely by string match on `MessageID` in `handleWebAPITriggerMessage`: [3](#0-2) 

Contrast this with the newer v2 HTTP trigger handler (`core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go`), which explicitly guards against this by checking for an existing in-flight `requestID` and returning `jsonrpc.ErrConflict` before storing a new callback: [4](#0-3) 

and by the vault gateway/JSON-RPC handlers, which use a `RequestReplayGuard` or an explicit `activeRequests[req.ID] != nil` check to reject duplicate/in-flight request IDs: [5](#0-4) [6](#0-5) 

Because the legacy WebAPI trigger path lacks this check, if two concurrent requests (from the same or different requesters/workflows) happen to use the same `MessageID`, the second call's `h.savedCallbacks[msg.Body.MessageID] = ...` silently replaces the first pending callback. When a node later responds for that `MessageID`, `handleWebAPITriggerMessage` will look up whatever callback currently occupies that map slot and deliver the response to it — potentially delivering requester A's node response to requester B's HTTP callback (cross-caller response confusion), or losing requester A's response entirely.

### Impact Explanation
This is analogous to the `orderId` duplication issue: a client-controlled identifier that should uniquely correlate a request to its response is not validated for uniqueness on the unprivileged-facing ingestion path. The consequence here is response misdelivery/loss for legacy WebAPI trigger requests rather than fund movement, but it does map to the "cross-user response confusion" category called out in the validation criteria, since a workflow response intended for one caller could be routed to another caller's connection.

### Likelihood Explanation
Exploitability depends on how `MessageID` is generated by legitimate upstream clients (e.g., whether it is a random UUID chosen by the caller or a predictable value). Because `HandleLegacyUserMessage`/`MethodWebAPITrigger` is marked as the legacy path (the v2 handler that has since added the duplicate-ID protection appears to be the actively maintained replacement), likelihood of this exact legacy code path being reachable from a real unprivileged client in current production configurations is uncertain from static analysis alone — I could not fully trace, within the available tool budget, the exact ingress (HTTP proxy handler) that maps an inbound end-user request into a `MessageID` used by `HandleLegacyUserMessage`, so it is unclear if the ID is always caller-supplied end-to-end or partially server-generated.

### Recommendation
Apply the same duplicate-ID guard used in `http_trigger_handler.go`/`confidentialrelay/handler.go` to `HandleLegacyUserMessage`: check `h.savedCallbacks[msg.Body.MessageID]` for an existing entry under the lock and reject (return a conflict error to the caller) instead of overwriting it, mirroring the fix pattern already present elsewhere in the codebase.

### Proof of Concept
Not fully constructible with the available read-only access — I could not confirm, within this session, the exact unprivileged HTTP entrypoint that constructs the `api.Message` consumed by `HandleLegacyUserMessage` and whether `MessageID` there is always attacker-influenced end-to-end. A concrete PoC would require: (1) verifying the ingress handler that sets `msg.Body.MessageID` from an end-user request, (2) issuing two concurrent legacy WebAPI trigger requests with the same `MessageID` (via that ingress), and (3) confirming that the second request's callback map entry replaces the first, causing the first requester to never receive a response (or to receive the second's response) once `handleWebAPITriggerMessage` fires.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageID]
	delete(h.savedCallbacks, msg.Body.MessageID)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JSONRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageID) == 0 || len(m.Body.MessageID) > MessageIDMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageID, NullChar) {
		return errors.New("message ID ending with null bytes")
	}

func (h *httpTriggerHandler) setupCallback(ctx context.Context, requestID string, callback handlers.Callback, requestStartTime time.Time, workflowID string) (<-chan struct{}, error) {
	h.callbacksMu.Lock()
	defer h.callbacksMu.Unlock()

	if _, found := h.callbacks[requestID]; found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, fmt.Sprintf("requestID: %s has already been used. Ensure the requestID is unique for each request.", requestID), callback)
		return nil, fmt.Errorf("in-flight request ID: %s", requestID)

func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}
