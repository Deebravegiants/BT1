### Title
OIDC Token Exchange Grants Authenticated Session Despite Missing Identity Claim, Bypassing Intended Rejection - (File: core/sessions/oidcauth/oidc.go)

### Summary
In `handleTokenExchange`, when the OIDC ID token's `email` claim is missing or not a string, the handler logs the error and writes an HTTP 500 response via `c.String(...)`, but is missing the `return` statement that every other failure branch in this function has. Execution falls through and continues to compute the user's RBAC role from the `groups`/ID claims, insert a row into `oidc_sessions` with `user_email = ""`, and set the session cookie — completing a fully valid, cookie-backed authenticated session with an assigned role but no identity.

### Finding Description
`handleTokenExchange` performs a sequence of validation steps (state check, token exchange, ID token verification, claim extraction), each of which correctly aborts with `return` on failure — except the email-claim check: [2](#0-1) 
Because `return` is omitted here, the function proceeds to:
1. Map the `groups`/ID claims to a role via `IDClaimsToUserRole` (unaffected by the missing email; still may resolve to any of Admin/Edit/Run/View based on group claim matches). [3](#0-2) 
2. Insert a new row into `oidc_sessions` with `user_email = ""` (lowercased empty string) and the resolved role. [4](#0-3) 
3. Set the session cookie (`webauth.SessionIDKey`) and persist it via `ginSession.Save()`. [5](#0-4) 

Downstream, `AuthorizedUserWithSession` reconstructs the `clsessions.User{Email, Role}` object directly from the `oidc_sessions` row with no re-validation that `Email` is non-empty: [6](#0-5)  This `User` is placed into the Gin context and used for RBAC checks in `RequiresRunRole`, `RequiresEditRole`, and `RequiresAdminRole`, all of which gate solely on `user.Role`, never on `user.Email`: [7](#0-6) 

This is structurally analogous to the reported Flux Operator bug: an identity attribute expected to be populated from OIDC claims (there: `username`/`groups` for impersonation; here: `email` for user identity) can end up empty due to a provider/claim mismatch, and the code fails to treat that as an authentication failure — it fails open rather than closed, granting a working session with elevated privileges.

### Impact Explanation
Any user who can complete a valid OIDC login flow against the configured provider (i.e., anyone the operator's identity provider authenticates) but whose token lacks an `email` claim — or whose `email` claim is a non-string type — will still be granted a persisted, cookie-backed session with `Role` derived from whatever `groups` claim they carry. Since RBAC enforcement (`RequiresAdminRole`, etc.) checks only `Role`, this session functions with full permissions of that role (potentially Admin) despite the identity being empty. This breaks the assumption that every authenticated session maps to a known, auditable email identity, undermining both authorization integrity and audit-log attribution (`audit.AuthLoginSuccessNo2FA` is logged with `email=""`) [8](#0-7) .

### Likelihood Explanation
Exploitation requires the operator's OIDC provider to be configured such that some authenticated users' ID tokens lack an `email` claim (or return it in a non-string form) while still supplying a `groups`/ID claim that maps to a privileged role — a configuration mismatch scenario, not an attacker-controlled one, mirroring the prerequisite in the referenced advisory ("cluster admins must configure ... a provider that issues tokens lacking the expected claims"). Given that OIDC deployments frequently vary claim sets by provider/scope configuration, this is a realistic misconfiguration rather than a purely theoretical one, but it is not exploitable by an unprivileged attacker without such a provider/claims mismatch already existing.

### Recommendation
Add `return` immediately after the `c.String(http.StatusInternalServerError, "Failed to get email from claims")` call at `core/sessions/oidcauth/oidc.go:229` so the handler aborts the flow when the `email` claim is missing or invalid, consistent with every other validation branch in `handleTokenExchange`. Additionally, consider explicitly rejecting empty-string `email` (not just missing/wrong-typed) before persisting the `oidc_sessions` row, and consider adding a defense-in-depth check in `AuthorizedUserWithSession` to reject sessions with an empty `UserEmail`.

### Proof of Concept
1. Configure `WebServer.AuthenticationMethod = 'oidc'` with a provider whose ID tokens include a `groups` claim (e.g., containing `NodeAdmins`) but omit the `email` claim.
2. As an authenticated user of that provider, complete the OIDC flow to `POST /oidc-exchange` with a valid `code`/`state`.
3. In `handleTokenExchange`, the `claims["email"].(string)` type assertion fails at `core/sessions/oidcauth/oidc.go:226-230`; the missing `return` allows execution to continue.
4. `IDClaimsToUserRole` resolves the role to `UserRoleAdmin` from the `groups` claim `core/sessions/oidcauth/oidc.go:233-245`.
5. A row is inserted into `oidc_sessions` with `user_email = ''` and `user_role = 'admin'`, and the session cookie is set `core/sessions/oidcauth/oidc.go:247-271`.
6. Subsequent requests using that session cookie pass `AuthenticateBySession` → `AuthorizedUserWithSession` → `RequiresAdminRole`, since only `Role` is checked, granting full admin API access despite an empty user identity.

Note: I was unable to further verify at runtime whether Gin's double-write (the earlier `c.String` 500 plus the later `c.JSON` 200) causes the client to observe an error or a success response for the initial exchange call; regardless, the session cookie and DB row are created server-side once execution falls through, so the resulting session is valid for subsequent authenticated requests.

// AuthorizedUserWithSession will return the API user associated with the Session ID if it
// exists and hasn't expired
func (oi *oidcAuthenticator) AuthorizedUserWithSession(ctx context.Context, sessionID string) (clsessions.User, error) {
	if len(sessionID) == 0 {
		return clsessions.User{}, errors.New("session ID cannot be empty")
	}
	var foundUser clsessions.User
	err := sqlutil.TransactDataSource(ctx, oi.ds, nil, func(tx sqlutil.DataSource) error {
		// Query the oidc_sessions table for given session ID, user role and email are saved after the id claims is provided and validated
		var foundSession struct {
			UserEmail string
			UserRole  clsessions.UserRole
			Valid     bool
		}
		if err := tx.GetContext(ctx, &foundSession,
			"SELECT user_email, user_role, created_at + $2 >= now() as valid FROM oidc_sessions WHERE id = $1",
			sessionID, oi.config.SessionTimeout().Duration(),
		); err != nil {
			if errors.Is(err, sql.ErrNoRows) {
				return clsessions.ErrUserSessionExpired
			}
			return err
		}
		if !foundSession.Valid {
			// Sessions expired, purge
			return clsessions.ErrUserSessionExpired
		}
		foundUser = clsessions.User{
			Email: foundSession.UserEmail,
			Role:  foundSession.UserRole,
		}
		return nil
	})
	if err != nil {
		if errors.Is(err, clsessions.ErrUserSessionExpired) {
			if _, execErr := oi.ds.ExecContext(ctx, "DELETE FROM oidc_sessions WHERE id = $1", sessionID); execErr != nil {
				oi.lggr.Errorf("error purging stale OIDC session: %v", execErr)
			}
		}
		return clsessions.User{}, err
	}
	return foundUser, nil
}
