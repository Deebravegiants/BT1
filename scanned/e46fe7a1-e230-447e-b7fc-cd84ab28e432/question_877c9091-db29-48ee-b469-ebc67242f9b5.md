In intent-signer-nep413.ts, signIntent embeds `signer_id: intent.signer_id ?? this.accountId` into the JSON message that gets NEP-413 hashed and signed, meaning any caller-supplied intent.signer_id overrides this.accountId entirely with no check that it matches the NEAR account actually controlling signMessageFn's key. Can an unprivileged caller construct an IntentPayload with signer_id set to a victim NEAR account (e.g. 'victim.near') while signMessageFn signs with the attacker's own NEAR keypair (accountId='attacker.near'), so the produced MultiPayloadNep413's payload.message contains signer_id='victim.near' but public_key/signature belong to attacker.near, breaking signer_id == account-that-controls(public_key)? Proof idea: vitest test constructing IntentSignerNEP413 with accountId='attacker.near' and a signMessageFn using attacker's keypair, then calling signIntent({signer_id:'victim.near', ...}), asserting the returned payload.message JSON contains signer_id 'victim.near' while public_key corresponds to attacker's key. Impact: Critical, intent manipulation letting an attacker forge intents claiming a victim account authorized them.
