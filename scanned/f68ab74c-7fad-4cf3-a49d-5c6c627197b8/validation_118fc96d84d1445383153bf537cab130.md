Based on my research, I found a valid analog in the chainlink codebase's External Initiator API.

### Title
Unmasked External Initiator credentials disclosed to any authenticated user regardless of role via `GET /v2/external_initiators` - (File: core/web/router.go, core/web/external_initiators_controller.go, core/web/presenters/external_initiators.go)

### Summary
The Jenkins Dingding plugin bug class (CWE-200/312: sensitive credential displayed without masking to users who should not see it) has a direct analog in chainlink's `ExternalInitiatorsController.Index` endpoint. Unlike the `Create` and `Destroy` actions on the same resource, the list endpoint is not gated by any role check, so any authenticated user — including the lowest-privileged `View` role — can retrieve the `AccessKey` and `OutgoingToken` credentials of every External Initiator registered on the node.

### Finding Description
In the route table, the External Initiator routes are registered as: [1](#0-0) 

Notice that `GET /external_initiators` (`Index`) has no `auth.RequiresEditRole` or `auth.RequiresAdminRole` wrapper, while `POST` (`Create`) and `DELETE` (`Destroy`) do. The only gate applied is the generic `auth.Authenticate` middleware for the `/v2` group, which accepts any valid session or API token regardless of role.

The `Index` handler returns the full list of initiators using `presenters.ExternalInitiatorResource`: [2](#0-1) 

That presenter includes the plaintext `AccessKey` and `OutgoingToken` fields with no redaction: [3](#0-2) 

This is confirmed by the existing test, which shows these fields returned as-is to any client hitting the endpoint: [4](#0-3) 

By contrast, other sensitive-config surfaces in the same codebase are deliberately redacted (e.g., secrets TOML rendering as `xxxxx`): [5](#0-4) 

This shows the project has an established redaction convention for credentials elsewhere, but it was not applied to the External Initiator listing endpoint's authorization/masking.

### Impact Explanation
`AccessKey` and `OutgoingToken` are authentication material: `AccessKey` (together with the initiator's `Secret`, not returned here but derivable to authenticate as that EI) is used by external initiators to call back into node job trigger endpoints, and `OutgoingToken` is a bearer credential the node sends outward to the initiator's URL. A low-privileged authenticated user (e.g., `View` role, which is meant for read-only, non-sensitive access) can enumerate this data for every External Initiator configured on the node, enabling impersonation of legitimate initiators or replay of outgoing webhook tokens, and information disclosure beyond the intended role boundary.

### Likelihood Explanation
Requires only a valid, low-privileged authenticated session/API token (any role) and a single unauthenticated-role-check `GET /v2/external_initiators` call — no special network position or elevated privileges needed. Feature gate is `ExternalInitiatorsEnabled`, which needs to be true, but no role restriction otherwise applies. This is directly reachable from any unprivileged client that merely has a valid low-privileged session, matching the report's threat model (unprivileged actor viewing job/config data that should be masked/gated).

### Recommendation
Add `auth.RequiresEditRole` (matching `Create`/`Destroy`) or at minimum `auth.RequiresAdminRole` to the `GET /v2/external_initiators` route in `core/web/router.go`. Additionally, consider omitting or redacting `AccessKey`/`OutgoingToken` in `presenters.ExternalInitiatorResource` for list views, following the same masking convention used for `secrets-full-redacted.toml`.

### Proof of Concept
1. Create a Chainlink node user with the lowest role (`View`).
2. Authenticate as that user and obtain a session/API token.
3. Issue `GET /v2/external_initiators` with that session.
4. Observe the JSON response contains `accessKey` and `outgoingToken` fields in plaintext for every registered External Initiator, as demonstrated by the existing test assertions at [6](#0-5) , even though this role should not be permitted to view or manage External Initiators (compare to `Create`/`Destroy` which enforce `RequiresEditRole`).

**Note on completeness:** I was unable to fully confirm within available tool calls whether `View` role is indeed the lowest privilege tier and definitively distinct from `Edit`/`Admin` in `core/sessions/user.go`, though grep confirmed `UserRoleView/Edit/Admin` constants exist there; a Devin session with full file access would be needed to verify the exact role hierarchy and enumeration values if further certainty is required.

```go
func (eic *ExternalInitiatorsController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	externalInitiators, count, err := eic.App.BridgeORM().ExternalInitiators(ctx, offset, size)
	resources := make([]presenters.ExternalInitiatorResource, 0, len(externalInitiators))
	for _, initiator := range externalInitiators {
		resources = append(resources, presenters.NewExternalInitiatorResource(initiator))
	}

	paginatedResponse(c, "externalInitiators", size, page, resources, count, err)
}
```
