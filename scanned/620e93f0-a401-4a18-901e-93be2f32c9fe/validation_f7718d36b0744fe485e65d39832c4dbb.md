### Title
Metering balance under-decrements when capability spend exceeds earmarked reserve, allowing quota/reserve bypass for subsequent workflow steps - ([File: core/services/workflows/metering/metering.go])

### Summary
The CRE workflow metering `Report.Settle` function refunds the unused portion of an earmarked credit deduction back to the local `balanceStore` by computing `step.Deduction.Sub(spentCredits)` and calling `balance.Add(...)`. When actual node-reported spend (`spentCredits`) exceeds the amount that was earmarked in `Deduct` (`step.Deduction`), this delta is negative, `balance.Add` rejects negative amounts, and the local balance is silently left un-decremented for the overage — the same class of bug as the Yeti finding, where a "whole vs. delta" accounting mismatch lets more of a resource be credited/consumed than what was actually backed.

### Finding Description
`Deduct` earmarks credits from the local `balanceStore` up-front via `r.balance.Minus(...)` [1](#0-0) , and separately via `ByDerivedAvailability` for concurrency-derived limits [2](#0-1) . Later, `Settle` aggregates real node-reported spend values (`spentCredits`) and attempts to true-up the local balance: [3](#0-2) 

The refund logic assumes `spentCredits <= step.Deduction` (i.e., actual spend never exceeds the amount reserved for that step). If that assumption is violated — even in a legitimate, non-malicious scenario such as a capability's median SpendValue coming in slightly above the pre-computed `ByDerivedAvailability` limit due to normal price/gas variance between the time of `Deduct` and the time nodes report actual spend — `step.Deduction.Sub(spentCredits)` is negative. `balanceStore.Add` explicitly rejects negative amounts and returns `ErrInvalidAmount` [4](#0-3) , and `Settle` only logs this as an "invariant" violation without adjusting the balance at all [5](#0-4) .

This is the same accounting flaw pattern as the Yeti H-02 report: instead of correctly capping/limiting the additional amount by what was actually available/reserved, the code performs an operation that is simply dropped when the precondition is violated, leaving the tracked local balance higher than what true consumption warrants. `spent` bookkeeping via `AddSpent(spentCredits)` [6](#0-5)  is unconditional and correct for the eventual billing receipt (`GetSpent()` used in `SendReceipt`) [7](#0-6) , but the *local* `balance.Get()` value used to authorize subsequent `Deduct` calls within the same execution — via `getMaxSpendForInvocation` [8](#0-7)  — remains artificially inflated relative to the true remaining reserve.

### Impact Explanation
Because `getMaxSpendForInvocation`/`ByDerivedAvailability` gate subsequent capability invocations on the stale, inflated local balance, a single workflow execution can authorize more capability calls (each carrying real gas/compute cost) than the credit amount actually reserved from the billing service via `Reserve`/`ReserveCredits` [9](#0-8) . This is a quota/reserve-bypass condition: workflow steps that should have been blocked by insufficient local balance are instead permitted, letting an unprivileged workflow owner cause resource/fund consumption beyond what was actually authorized for that execution.

### Likelihood Explanation
This requires only normal operating conditions, not a malicious node: any legitimate deviation between the `Deduct`-time estimate (`ByDerivedAvailability`, which derives a limit from `userSpendLimit`/open concurrent slots before the capability executes) and the capability's later, node-reported actual spend (`Settle`) that happens to exceed that estimate will trigger the silently-dropped refund. Gas price or compute-cost variance between reservation and settlement time makes this a plausible, non-adversarial occurrence rather than an edge case requiring attacker control.

### Recommendation
Mirror the Yeti fix: clamp the amount involved instead of letting the operation silently no-op when the precondition is violated. In `Settle`, when `spentCredits > step.Deduction`, explicitly subtract the excess from the local balance (allowing it to go to zero, and tracking/reporting the shortfall) rather than skipping the balance adjustment:
```go
diff := step.Deduction.Sub(spentCredits)
if diff.IsNegative() {
    // spend exceeded reserve: properly deduct the excess instead of no-op
    _ = r.balance.Minus(diff.Abs())
    r.lggr.Warnw("spend exceeded reserve; deducting excess from local balance", ...)
} else if err := r.balance.Add(diff); err != nil {
    r.lggr.Info("invariant: spend exceeded reserve")
}
```
This ensures the local balance used for gating subsequent `Deduct` calls always accurately reflects true consumption, closing the quota-bypass window.

### Proof of Concept
Not directly exploitable by a crafted PoC without control over node-reported `SpendValue`; the finding is a logic/accounting analog reachable through legitimate variance between `Deduct`-time and `Settle`-time spend calculations:
1. Workflow owner submits an execution with `ByDerivedAvailability` limiting a step to `X` credits based on current balance/slot split [10](#0-9) .
2. Capability nodes report actual `SpendValue`s whose median, after gas/price normalization, converts to `Y > X` credits [11](#0-10) .
3. `Settle` computes `step.Deduction.Sub(spentCredits)` = negative, `balance.Add` fails and is only logged [12](#0-11) ; local balance remains at its post-`Deduct` value instead of being further reduced by `(Y-X)`.
4. Subsequent steps in the same execution call `getMaxSpendForInvocation`, which reads the inflated `r.balance.Get()` [13](#0-12) , authorizing more spend than the true remaining reserve should allow.

func ByDerivedAvailability(
	userSpendLimit decimal.NullDecimal,
	openConcurrentCallSlots int,
	info capabilities.CapabilityInfo,
	config *values.Map,
) func(string, *Report) ([]capabilities.SpendLimit, error) {
	return func(ref string, r *Report) ([]capabilities.SpendLimit, error) {
		step := ReportStep{
			CapabilityID:     info.ID,
			Deduction:        decimal.Zero,
			AggregatedSpends: make(map[string]AggregatedStepDetail),
		}

		defer func() {
			r.steps[ref] = step
		}()

		limit, err := r.getMaxSpendForInvocation(userSpendLimit, openConcurrentCallSlots)
		if err != nil {
			return nil, err
		}

		if !limit.Valid {
			return []capabilities.SpendLimit{}, nil
		}

		step.Deduction = limit.Decimal

		// if in metering mode, exit early without modifying local balance
		if r.meteringMode {
			return []capabilities.SpendLimit{}, nil
		}

		return r.creditToSpendingLimits(info, config, limit.Decimal), r.balance.Minus(limit.Decimal)
	}

func (r *Report) getMaxSpendForInvocation(
	userSpendLimit decimal.NullDecimal,
	openConcurrentCallSlots int,
) (decimal.NullDecimal, error) {
	nullCapSpendLimit := decimal.NewNullDecimal(decimal.Zero)
	nullCapSpendLimit.Valid = false

	if openConcurrentCallSlots == 0 {
		// invariant: this should be managed by the consumer (engine)
		return nullCapSpendLimit, ErrNoOpenCalls
	}

	if !r.reserved {
		return nullCapSpendLimit, ErrNoReserve
	}

	if r.meteringMode {
		return nullCapSpendLimit, nil
	}

	// Split the available local balance between the number of concurrent calls that can still be made
	spendLimit := r.balance.Get().Div(decimal.NewFromInt(int64(openConcurrentCallSlots)))

	if userSpendLimit.Valid {
		spendLimit = decimal.Min(spendLimit, userSpendLimit.Decimal)
	}

	return decimal.NewNullDecimal(spendLimit), nil
}

// Add increases the current credit balance.
func (bs *balanceStore) Add(amount decimal.Decimal) error {
	bs.mu.Lock()
	defer bs.mu.Unlock()

	if amount.LessThan(decimal.Zero) {
		return ErrInvalidAmount
	}

	bs.balance = bs.balance.Add(amount)

	return nil
}
