### Title
JWT Replay Guard Uses Non-Atomic Check-Then-Record, Allowing Concurrent Replay of a Single JWT in HTTP Trigger Workflow Authorization - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

### Summary
The gateway's `WorkflowMetadataHandler.Authorize` function, which authenticates inbound HTTP-trigger requests from unprivileged external clients, is supposed to enforce a strict "check-then-record" order to prevent JWT replay. However, the `jwtReplayCache.isReplay()` check and `jwtReplayCache.recordUsage()` write are two independently-locked operations rather than one atomic operation, so the enforcement of "a JWT can only be used once" is not guaranteed under concurrency — mirroring the reported bug class where a required sequential dependency between two state-mutating operations is not enforced by the code.

### Finding Description
`Authorize` in [1](#0-0)  validates a JWT, checks replay via `h.jwtCache.isReplay(claims.ID)`, verifies the signer is an authorized key, and finally calls `h.jwtCache.recordUsage(claims.ID)` to mark the JWT as spent.

The underlying `jwtReplayCache` implements these two operations with separate lock scopes: [2](#0-1) 

`isReplay` takes an `RLock`, reads, and releases; `recordUsage` later takes a separate `Lock` and writes. There is no atomic "check-and-record" primitive analogous to the one used elsewhere in the codebase for the same purpose. By contrast, the Vault capability's `RequestReplayGuard.CheckAndRecord` performs the lookup and the insertion under a single lock, making check-and-record atomic and safe against concurrent replay: [3](#0-2) 

This shows the codebase is aware of, and elsewhere implements, the correct atomic pattern — but the HTTP-trigger JWT replay cache does not enforce it. Because `isReplay` and `recordUsage` are not combined into one critical section, two (or more) concurrent `Authorize` calls carrying the identical JWT (same `jti`) can each execute `isReplay` before either has executed `recordUsage`, both observing "not yet seen" and both succeeding.

### Impact Explanation
An unprivileged external caller who obtains or captures a single valid signed JWT for an HTTP trigger request can send multiple concurrent copies of the same request to the gateway. Due to the non-atomic check/record gap, more than one of these requests can bypass the intended "each JWT usable exactly once" replay protection and be treated as authorized, each dispatching the workflow-trigger request to the DON. This defeats the anti-replay control that is the specific security guarantee this cache exists to provide, enabling duplicate/unauthorized triggering of workflow executions from a single captured token. This maps to "unauthorized job run" / authentication bypass category from the validation criteria.

### Likelihood Explanation
Exploitation requires only that an attacker (or any client possessing one valid JWT+request pair) issue the request twice in quick succession/concurrently — no special network position or privileged access is needed, since this is exposed at the internet-facing HTTP trigger gateway path (`HandleUserTriggerRequest` → `Authorize`). The race window is small (two independent mutex acquisitions performed in rapid succession), but is fully within reach of a remote unprivileged actor via ordinary concurrent HTTP requests, making likelihood realistic though it depends on winning a narrow timing window.

### Recommendation
Combine the replay check and record operation into a single atomic critical section under one lock (mirroring `RequestReplayGuard.CheckAndRecord` in `core/capabilities/vault/request_replay_guard.go`), e.g. a `CheckAndRecord(jti)` method on `jwtReplayCache` that, while holding the write lock, checks for existence and inserts on absence, returning true/false for "already seen." Update `Authorize` in `workflow_metadata_handler.go` to call this atomic method instead of separate `isReplay`/`recordUsage` calls.

### Proof of Concept
1. Obtain one valid signed JWT for a given `req` (`jti = X`) intended for the HTTP trigger endpoint.
2. Fire two (or more) concurrent HTTP requests to the gateway trigger endpoint, both carrying the same JWT/request pair, timed so that both reach `WorkflowMetadataHandler.Authorize` before either completes.
3. Both goroutines execute `h.jwtCache.isReplay(claims.ID)` [4](#0-3)  concurrently; since the cache entry for `jti=X` does not exist yet, both return `false`.
4. Both proceed to signer/authorized-key validation and both eventually call `recordUsage`, but by then both have already returned successful `*gateway.AuthorizedKey` results and dispatched the request onward — i.e., the same JWT was accepted twice, defeating the intended single-use replay guarantee tested for in `TestWorkflowMetadataHandler_Authorize`'s "JWT replay protection" subtest, which only validates the *sequential* (non-concurrent) case [5](#0-4) .

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}

func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}
