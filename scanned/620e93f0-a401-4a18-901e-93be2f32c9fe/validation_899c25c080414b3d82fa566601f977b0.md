### Title
CORS wildcard-origin allowlist bypass via unanchored suffix match - ([File: core/services/gateway/network/httpserver.go])

### Summary
The gateway's internet-facing HTTP server implements CORS origin allowlisting with a wildcard suffix check that lacks a domain-boundary anchor. A crafted origin whose hostname merely *ends with* the allowed suffix (rather than being a true subdomain of it) is treated as an allowed origin, letting an attacker-controlled site bypass the `CORSAllowedOrigins` allowlist.

### Finding Description
`isAllowedOrigin` in `core/services/gateway/network/httpserver.go` handles wildcard entries (`*.domain.com`) like this: [1](#0-0) 

```go
// check for wildcard host match (e.g., *.remix.com)
if strings.HasPrefix(allowedHost, "*.") {
    allowedHost = allowedHost[2:]
    if strings.HasSuffix(originHost, allowedHost) {
        return true
    }
}
```

`strings.HasSuffix` performs a raw substring suffix comparison with no requirement that the character preceding the matched suffix be a `.` (or that `originHost` equal `allowedHost`). Consequently a hostname such as `evilethereum.org` satisfies `strings.HasSuffix("evilethereum.org", "ethereum.org")` even though it is a completely unrelated registrable domain, not a subdomain of `ethereum.org`. This is the same bug class as CVE-2026-80213: a length/boundary check that is supposed to constrain matching to a well-formed hierarchical label boundary is missing, so attacker-controlled data (a look-alike hostname) is treated as if it belonged to a trusted domain, bypassing the allowlist.

This function is invoked directly from `handleRequest`, the entry point for every request the internet-facing gateway HTTP server receives from unprivileged clients/browsers: [2](#0-1) 

If the crafted `Origin` header passes the check, the server reflects it back verbatim in `Access-Control-Allow-Origin`, so any browser will permit the attacker's page to read cross-origin responses from the gateway.

The existing test suite exercises the negative case for a *different* kind of malformed suffix (`ethereum.remix.org` doesn't end with `ethereum.org`) but never exercises the boundary-less "prefix concatenation" case (`evilethereum.org` ends with `ethereum.org`), so this bypass is not caught by current tests: [3](#0-2) 

### Impact Explanation
An operator who configures a wildcard CORS allowlist entry such as `https://*.ethereum.org` intends to permit only genuine subdomains of `ethereum.org`. Due to the missing boundary check, any attacker who registers a domain that merely ends with that string (e.g. `evilethereum.org`, `fake-ethereum.org` is not a match, but `xethereum.org` is) can have arbitrary origins whitelisted. This is an allowlist bypass on the gateway's user-facing HTTP endpoint, enabling an unprivileged, unrelated website to have its origin reflected into `Access-Control-Allow-Origin`, breaking the intended cross-origin isolation for the gateway API (which processes JSON-RPC-style requests routed to node capabilities/handlers). This can allow cross-user response confusion / unauthorized reading of gateway responses from a browser context the operator did not intend to trust.

### Likelihood Explanation
Exploitability depends entirely on operator configuration of `CORSAllowedOrigins` with a wildcard entry (`*.domain.tld`), which is a documented, supported configuration option (see `CORSEnabled`/`CORSAllowedOrigins` fields and sample configs). Any operator using a wildcard CORS rule is affected without additional action from the attacker beyond registering/hosting a domain with the right suffix — no privileged access is required, matching the CVE's AC:H / PR:N / UI:N profile (requires attacker to control a specifically-crafted domain name, but no user interaction or privilege needed beyond that).

### Recommendation
Anchor the wildcard suffix match to a real label boundary, e.g.:
```go
if strings.HasPrefix(allowedHost, "*.") {
    suffix := allowedHost[1:] // ".ethereum.org"
    if originHost == suffix[1:] || strings.HasSuffix(originHost, suffix) {
        return true
    }
}
```
so `originHost` must equal `ethereum.org` or end with `.ethereum.org`, never merely with the raw substring `ethereum.org`. Add a regression test asserting that origins like `https://evilethereum.org` are rejected against an allowlist entry of `https://*.ethereum.org`.

### Proof of Concept
1. Configure the gateway HTTP server with `CORSEnabled = true` and `CORSAllowedOrigins = ["https://*.ethereum.org"]`.
2. From a browser, load a page hosted at `https://evilethereum.org`, and issue a fetch/XHR request to the gateway endpoint with header `Origin: https://evilethereum.org`.
3. Observe the gateway response includes `Access-Control-Allow-Origin: https://evilethereum.org`, because `isAllowedOrigin` returns true via `strings.HasSuffix("evilethereum.org", "ethereum.org")` — even though `evilethereum.org` is not a subdomain of `ethereum.org`.
4. The browser now permits the attacker's page at `evilethereum.org` to read the gateway's response cross-origin, bypassing the intended allowlist restriction.
