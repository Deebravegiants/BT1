This confirms Polkadot's GRANDPA finality gadget provides **deterministic, provably-final blocks** — once a block is finalized, "it can't be reverted" [1](#0-0) [2](#0-1) . This is fundamentally different from Polygon's probabilistic finality model that the Lens report relies on, and it substantially limits (but does not eliminate) the practical window for this vulnerability class in Polkadot SDK chains.

That said, the underlying pattern — **referencing a governance object purely by a sequentially-assigned index rather than by content hash** — does exist in `pallet-democracy`.

### Title
Referencing public proposals by sequential `PropIndex` instead of content hash makes `second()`/`vote()` vulnerable to pre-finality reorg misassignment - (File: `substrate/frame/democracy/src/lib.rs`)

### Summary
`pallet-democracy`'s public-proposal queue assigns each proposal a monotonically increasing `PropIndex` that is unrelated to the proposal's content, and lets any signed account "second" (financially back) a proposal by supplying only that index.

### Finding Description
`propose()` reads the next `PropIndex` from `PublicPropCount`, increments it, and stores `(index, proposal, who)` in `PublicProps`, with the deposit tracked purely under `DepositOf<PropIndex>` [3](#0-2) . Critically, `second()` takes only a numeric `proposal: PropIndex` argument, looks up `DepositOf::<T>::get(proposal)`, and reserves the seconder's currency against whatever proposal currently occupies that index — it never checks the proposal's content or hash: [4](#0-3) . Likewise, `vote()` on a live referendum takes only a `ReferendumIndex`, with no content-hash binding [5](#0-4) , and `inject_referendum` assigns the next `ReferendumIndex` from a simple counter [6](#0-5) . The `pallet-referenda` successor pallet has the same shape: `submit()` assigns `index` from `ReferendumCount::<T, I>::mutate`, and both `place_decision_deposit(index)` and future votes reference only that numeric index, not the proposal hash [7](#0-6) [8](#0-7) .

This is the exact class of bug in the Lens report: an unprivileged actor submits a transaction that references an on-chain object purely by an auto-incrementing counter value. If two independently-submitted `propose()` transactions from different accounts (both permitted, since `SubmitOrigin` is not restricted to a single privileged account in the general case) get reordered across an unfinalized fork switch, the `PropIndex` that Bob intended to second for Alice's proposal A could instead be occupied by proposal B — and Bob's `second()` transaction, if replayed as-is against the new fork before it's dropped/rejected by the mempool, would back proposal B instead of A.

Notably, `pallet-collective` avoids this exact problem by keying its `Voting`/`ProposalOf` storage on the **proposal hash** itself rather than solely the sequential `ProposalIndex`; the numeric `index` there is only used as an added guard (`ensure!(voting.index == index, Error::WrongIndex)`) but the primary key is the content hash [9](#0-8) , so a reorg-induced index shuffle cannot cause a collective member to vote/second the wrong proposal — this is a mitigation pattern absent in `pallet-democracy`/`pallet-referenda`.

### Impact Explanation
If exploited, an account's `second()` deposit could end up backing (and financially supporting the tabling of) a proposal it never intended to support — potentially a malicious or unrelated Root-authority-changing proposal, since seconds influence which proposal is next tabled for referendum. Because seconding only reserves funds (recoverable) rather than irreversibly transferring value, the direct financial loss is bounded, but the governance-integrity impact (unintentionally supporting an unwanted runtime-upgrade or Root-origin proposal) could be significant.

### Likelihood Explanation
Likelihood is low in practice for finalized chains: GRANDPA provides deterministic finality, and any reorg capable of reordering two independent `propose()` calls could only occur among not-yet-finalized blocks within the very short window before GRANDPA finalizes (typically seconds), and well-behaved wallets/relays are expected to wait for finality before considering a `second()`/`vote()` call settled. There is no evidence of large post-finality reorgs on Polkadot/Kusama comparable to those documented for Polygon in the original report. This significantly reduces attacker feasibility compared to the Lens/Polygon scenario, and no privileged role is required to trigger the underlying condition — only the general uncertainty of unfinalized-fork reordering.

### Recommendation
Consider having `second()` (and the referenda index-referencing calls) additionally require and verify a caller-supplied hash of the proposal content, mirroring `pallet-collective`'s pattern of keying storage by `T::Hashing::hash_of(&proposal)` rather than relying solely on the sequential index, so that a fork/reorg-induced index reassignment cannot silently redirect a caller's action to different proposal content.

### Proof of Concept
1. Account A calls `Democracy::propose(proposal_X, deposit)` in block N, receiving `PropIndex = k` (from `PublicPropCount`).
2. Account B, observing block N, submits `Democracy::second(k)` intending to back `proposal_X`, included in block N+1.
3. Before block N (or N+1) is finalized by GRANDPA, a short-lived fork reorg occurs in which a different account C's `propose(proposal_Y, ...)` transaction is included first, so `proposal_Y` now occupies `PropIndex = k` on the canonical fork.
4. If B's already-signed `second(k)` transaction is retransmitted/re-included on the new fork before wallets/relays notice the reorg, B's deposit now backs `proposal_Y` instead of `proposal_X`, as `second()` never checks proposal content, only the numeric index [10](#0-9) .
