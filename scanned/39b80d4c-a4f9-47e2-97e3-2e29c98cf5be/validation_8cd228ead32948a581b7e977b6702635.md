### Title
Gateway skips ciphertext label/ownership verification on secret writes when the master public key isn't cached, optimistically assuming Vault Nodes will catch invalid ciphertexts - (File: `core/capabilities/vault/validator.go`)

### Summary
The gateway's `RequestValidator.validateWriteRequest` (used by `ValidateCreateSecretsRequest`/`ValidateUpdateSecretsRequest`/`ValidateEncryptedSecretsStructure`) is supposed to verify that a submitted TDH2 ciphertext is well-formed and, via `EnsureRightLabelOnSecret`, that its embedded label matches the workflow owner asserted in the request. This verification is silently skipped whenever `publicKey` is `nil`, which the code comments say happens "if the gateway cache isn't populated yet (immediately after gateway reboots)." The gateway optimistically assumes the downstream Vault Nodes will perform this check instead, exactly analogous to `_doSherX` optimistically assuming premiums will be paid rather than verifying it.

### Finding Description
`verifyEncryptedSecret` short-circuits and returns `(nil, nil)` — i.e., "valid, no error" — whenever `publicKey == nil`: [1](#0-0) 

`EnsureRightLabelOnSecret`, which is the function responsible for verifying that the ciphertext's label matches the claimed secret owner, relies on `verifyEncryptedSecret` and also bails out early when the ciphertext comes back `nil`: [2](#0-1) 

This is invoked from `validateWriteRequest`, the common gateway-side entry point for `CreateSecrets`/`UpdateSecrets` structural validation: [3](#0-2) 

The comment explicitly documents the optimistic assumption: "Ok to not validate in such cases, since this validation also runs on Vault Nodes." This mirrors the Sherlock report's root cause — an expensive/important check is skipped based on an optimistic assumption that another actor (Vault Nodes, in this case; protocols repaying debt, in the original) will make it safe, rather than the gateway enforcing the invariant itself.

### Impact Explanation
This is a genuine defense-in-depth gap rather than a definitively provable full authentication bypass, since the report itself acknowledges Vault Nodes independently re-run the same verification (per `vaulttypes` node-side validation paths referenced in the comment). However:
- The gateway is the internet-facing entry point that performs the owner-label check before/around authorization (`GatewayVaultRequestProcessor.ProcessRequest`, `ValidateStructureBeforeAuth → AuthorizeRequest`), so if this check is bypassed at the gateway layer, malformed/mislabeled ciphertexts can be forwarded and processed further in the pipeline (owner-scoped limiter registration, replay-guard, authorization) without the label-consistency guarantee holding.
- The window is not rare/contrived: the comment states it reliably occurs "immediately after gateway reboots" — a normal operational event, not an edge case — meaning the optimistic bypass is a routine post-restart condition, not a corner case.
- If Vault Node-side verification has any gap, timing difference, or is bypassed under the same conditions (e.g., a node also lacking the cached public key, or a race during rollout), a request with an incorrect owner label could pass gateway-side checks and reach further processing stages that assume label correctness.

### Likelihood Explanation
Likelihood is directly tied to an operational event (gateway restart/master-key cache miss) rather than requiring a rare race window, so the code path executes routinely. Whether it is exploitable end-to-end depends on the redundancy of Vault Node validation holding at all times, which I could not fully verify from the indexed code (node-side validation call sites were only partially visible).

### Recommendation
Do not treat a `nil` public key as "validation passed." Instead, either:
- Reject or defer the request (return a retryable error) until the gateway has the master public key cached, or
- Perform structural/label validation using a fallback verification path that does not require the live public key (e.g., decode-only structural checks) while still deferring full node-side cryptographic verification, but never silently short-circuit label/ownership checks with a `(nil, nil)` "success" result.
At minimum, document and monitor how often this fallback path is hit in production, and ensure Vault Node-side validation is unconditionally enforced (never skippable) so the gateway's optimistic skip cannot itself become the sole gate.

### Proof of Concept
Conceptual reproduction (not executed, based on code reading):
1. Restart/cold-start the gateway so `p.publicKey` (master TDH2 public key cache) is unpopulated, per the comment path exercised in `verifyEncryptedSecret`. [1](#0-0) 
2. Submit a `CreateSecrets`/`UpdateSecrets` gateway request whose `EncryptedValue` ciphertext has a label that does **not** match the `Id.Owner` field in the request (i.e., a mismatched/forged owner label).
3. `validateWriteRequest` → `EnsureRightLabelOnSecret` → `verifyEncryptedSecret(nil, secret)` returns `(nil, nil)`, and `EnsureRightLabelOnSecret` returns `nil` (no error) at line 326-328, so gateway-side structural validation reports success despite the owner-label mismatch. [4](#0-3) 
4. The request proceeds through the shared pipeline (`GatewayVaultRequestProcessor.ProcessRequest`) into authorization and downstream stages, relying solely on Vault Node-side re-verification (unverified in this review) to catch the mismatch. [5](#0-4) 

I was unable to fully confirm from the indexed code whether Vault Node-side verification is unconditionally enforced under the same public-key-unavailable condition, so I cannot state with certainty this results in a complete bypass end-to-end — this should be verified in a full checkout of the repository (node-side `ValidateCreateSecretsRequest`/`EnsureRightLabelOnSecret` call sites and OCR plugin validation in `core/services/ocr2/plugins/vault/plugin.go`).
