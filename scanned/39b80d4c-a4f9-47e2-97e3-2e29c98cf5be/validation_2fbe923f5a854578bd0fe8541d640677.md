### Title
Unpermissioned front-running of allowlisted Vault gateway requests via first-come digest replay guard - ([File: core/capabilities/vault/authorizer.go], [File: core/capabilities/vault/request_replay_guard.go])

### Summary
Vault gateway requests (`vault.secrets.list`, `vault.secrets.delete`, `vault.secrets.create`, `vault.secrets.update`) reaching the node from the internet-facing gateway are authorized purely by matching a content-derived request digest against an on-chain allowlist entry, with no binding of the digest to a specific network sender/connection. Because the replay guard treats a digest as "consumed" on first successful authorization, whichever client submits the exact allowlisted request body first — legitimate owner or unprivileged attacker who can reconstruct/observe the same params — wins the authorization and receives the response; the true owner's later, identical submission is then rejected as a replay.

### Finding Description
`AuthorizeRequest` in `allowListBasedAuth` computes `requestDigest` purely from the JSON-RPC method+params content and checks it against `workflowRegistrySyncer.GetAllowlistedRequests` entries populated on-chain by the owner calling `AllowlistRequest(digest, expiry)`: [1](#0-0) 

The returned `AuthResult.workflowOwner` is taken solely from the on-chain event's `Owner` field, not from any verification that the actual network caller submitting the JSON-RPC request to the gateway is that owner: [2](#0-1) 

The composite `Authorizer.AuthorizeRequest` then only additionally checks a replay guard keyed by digest and validates that secret owners inside the params match the "authorized" owner returned by the allowlist lookup — it never authenticates the identity of the HTTP/gateway sender itself: [3](#0-2) 

The replay guard is strictly first-come-first-served on the digest, with no sender/session binding at all: [4](#0-3) 

For `vault.secrets.list` and `vault.secrets.delete`, the params required to reproduce the exact digest are the owner address, namespace and key — fields that are frequently public/derivable (e.g., a known workflow owner address, default namespace) rather than secret material, unlike `create`/`update` requests whose ciphertext payload is attacker-unknown. This means an unprivileged network client hitting the gateway can pre-compute or observe the digest the legitimate owner will submit (or is about to submit, since the owner must first put it on-chain via a public transaction before use) and race to submit the identical JSON-RPC body to the gateway first.

The gateway handler treats whichever caller supplied the message as the recipient of the response, routing it back over the connection/gateway ID from which the request arrived with no cross-check to the on-chain owner's actual client identity: [5](#0-4) 

### Impact Explanation
An attacker who can predict or observe the parameters of an allowlisted `list`/`delete` request (owner address + namespace are public, especially once the owner's `AllowlistRequest` transaction is visible on-chain before the gateway request is sent) can front-run the legitimate owner:
- For `vault.secrets.list`: the attacker receives the response — the list of secret identifiers for that owner/namespace — instead of the legitimate owner (cross-user response confusion / unauthorized disclosure of secret identifiers).
- For `vault.secrets.delete`: the attacker can trigger deletion of the owner's secrets under the owner's own authorization, and the legitimate request is then rejected as a replay.
This is directly analogous to the Neko Network bug class: an unprivileged party consumes an authorization that was intended for another user, producing an action/response attributed to the victim but delivered to (or triggered by) the attacker.

### Likelihood Explanation
Exploitability depends on the attacker being able to reconstruct the exact JSON-RPC request body (and therefore digest) before or concurrently with the legitimate owner, which requires the request parameters to be predictable. For `create`/`update` this is unlikely since ciphertext is attacker-unknown, but for `list`/`delete` the parameters (owner, namespace, key) are frequently public or guessable, and the owner's on-chain `AllowlistRequest` transaction (containing the exact digest) is itself publicly visible before the gateway request is submitted, giving an attacker a race window. This is a genuine, reachable, unprivileged-client attack surface on the gateway path, though it requires network-level racing against the legitimate owner's gateway submission.

### Recommendation
Bind authorization to sender identity, not just request content:
- Require the gateway request to carry the owner's proof of possession (e.g., the JWT-based auth path already does this by cryptographically binding `request_digest` to a signed token) for the allowlist path as well, or deprecate the allowlist-only path in favor of always requiring signed/JWT-bound requests.
- If the allowlist path must remain for backward compatibility, additionally verify a signature over the request body from the owner's key (not just a digest match against a public on-chain digest), so that knowledge of the digest/params alone is insufficient to claim the authorization.
- Consider binding the replay-guard record to the specific gateway connection/session that will receive the response, invalidating cross-connection reuse.

### Proof of Concept
1. Owner calls `AllowlistRequest(digest, expiry)` on the `WorkflowRegistry` contract for a `vault.secrets.list` request digest computed from `{Owner: <ownerAddr>, Namespace: "main"}` — this transaction (and thus the plaintext digest-producing fields) is publicly visible on-chain.
2. Before the owner's client sends the actual JSON-RPC `vault.secrets.list` request to the gateway, an attacker constructs the identical JSON-RPC body (`{"method":"vault.secrets.list","params":{"owner":"<ownerAddr>","namespace":"main"}}`) and submits it to the public gateway endpoint.
3. `allowListBasedAuth.AuthorizeRequest` finds the matching on-chain allowlist entry, returns `AuthResult{workflowOwner: ownerAddr}`; `authorizer.AuthorizeRequest` records the digest in `RequestReplayGuard` and passes owner-validation (since `listReq.Owner == ownerAddr`).
4. `GatewayHandler.HandleGatewayMessage` processes the request and calls `gatewayConnector.SendToGateway(ctx, gatewayID, response)`, returning the owner's secret identifier list to the attacker's connection.
5. When the legitimate owner's client subsequently submits the same request, `RequestReplayGuard.CheckAndRecord` returns `ErrRequestAlreadySeen`, and the owner's request is rejected — confirming the attacker, not the owner, consumed the authorization.

func (a *authorizer) AuthorizeRequest(ctx context.Context, req jsonrpc.Request[json.RawMessage]) (*AuthResult, error) {
	authResult, err := a.authorizeRequest(ctx, req)
	if err != nil {
		return nil, err
	}
	if authResult == nil {
		err = errors.New("auth mechanism returned nil auth result")
		a.lggr.Errorw("auth mechanism returned nil auth result", "method", req.Method, "requestID", req.ID, "hasAuth", req.Auth != "")
		return nil, err
	}
	if err := a.replayGuard.CheckAndRecord(authResult.Digest(), authResult.ExpiresAt()); err != nil {
		a.lggr.Debugw("replay guard rejected request", "method", req.Method, "requestID", req.ID, "owner", authResult.AuthorizedOwner(), "digest", authResult.Digest(), "expiresAt", authResult.ExpiresAt(), "hasAuth", req.Auth != "", "error", err)
		return nil, err
	}
	if ownerErr := validateSecretOwnersMatchAuthorized(req, authResult.AuthorizedOwner()); ownerErr != nil {
		a.lggr.Errorw("owner binding rejected request", "method", req.Method, "requestID", req.ID, "owner", authResult.AuthorizedOwner(), "hasAuth", req.Auth != "", "error", ownerErr)
		return nil, ownerErr
	}
	a.lggr.Debugw("request authorized", "method", req.Method, "requestID", req.ID, "owner", authResult.AuthorizedOwner(), "digest", authResult.Digest(), "expiresAt", authResult.ExpiresAt(), "hasAuth", req.Auth != "")
	return authResult, nil
}

func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}

func (h *GatewayHandler) HandleGatewayMessage(ctx context.Context, gatewayID string, req *jsonrpc.Request[json.RawMessage]) (err error) {
	reqLggr := h.requestLogger(req, gatewayID)
	reqLggr.Debugw("received message from gateway", "req", req)

	var response *jsonrpc.Response[json.RawMessage]
	var authResult *AuthResult

	switch req.Method {
	case vaulttypes.MethodSecretsCreate, vaulttypes.MethodSecretsUpdate:
		publicKey, pkErr := h.getMasterPublicKey(ctx)
		if pkErr != nil {
			response = h.gatewayErrorResponse(ctx, gatewayID, req, pkErr)
			break
		}
		authorized, pipelineErr := h.requestProcessor.ProcessRequest(ctx, req, publicKey)
		if pipelineErr != nil {
			response = h.gatewayErrorResponse(ctx, gatewayID, req, pipelineErr)
			break
		}
		authResult = authorized.AuthResult
	case vaulttypes.MethodSecretsDelete, vaulttypes.MethodSecretsList:
		authorized, pipelineErr := h.requestProcessor.ProcessRequest(ctx, req, nil)
		if pipelineErr != nil {
			response = h.gatewayErrorResponse(ctx, gatewayID, req, pipelineErr)
			break
		}
		authResult = authorized.AuthResult
	case vaulttypes.MethodPublicKeyGet:
		response = h.handlePublicKeyGet(ctx, gatewayID, req)
	default:
		response = h.errorResponse(ctx, gatewayID, req, api.UnsupportedMethodError, errors.New("unsupported method: "+req.Method))
	}

	if response == nil {
		switch req.Method {
		case vaulttypes.MethodSecretsCreate:
			response = h.handleSecretsCreate(ctx, gatewayID, req)
		case vaulttypes.MethodSecretsUpdate:
			response = h.handleSecretsUpdate(ctx, gatewayID, req)
		case vaulttypes.MethodSecretsDelete:
			response = h.handleSecretsDelete(ctx, gatewayID, req)
		case vaulttypes.MethodSecretsList:
			response = h.handleSecretsList(ctx, gatewayID, req, authResult)
		}
	}

	if err = h.gatewayConnector.SendToGateway(ctx, gatewayID, response); err != nil {
		reqLggr.Errorw("Failed to send message to gateway", "error", err)
		return err
	}

	reqLggr.Infow("Sent message to gateway", "resp", response)
	h.metrics.requestSuccess.Add(ctx, 1, metric.WithAttributes(
		attribute.String("gateway_id", gatewayID),
	))
	return nil
