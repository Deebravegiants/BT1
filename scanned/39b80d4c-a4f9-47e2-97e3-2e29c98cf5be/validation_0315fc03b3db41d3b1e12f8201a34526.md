## Finding: LDAP Authentication Bypass via Empty Password (Unauthenticated Bind)

The Symfony CVE-2016-2403 bug class ("logging in with an empty password and valid username... triggers an unauthenticated bind") has a direct analog in this codebase's LDAP authentication provider.

### Title
LDAP CreateSession accepts empty password, triggering an unauthenticated LDAP bind that bypasses credential verification - (File: core/sessions/ldapauth/ldap.go)

### Summary
`ldapAuthenticator.CreateSession` forwards the user-supplied password directly to the LDAP client's `Bind` call without ever checking whether it is empty.

### Finding Description
The `/sessions` endpoint is reachable by any unauthenticated client via `unauth.POST("/sessions", sc.Create)` [1](#0-0)  which calls into `SessionsController.Create`, binding the raw request body (`email`, `password`) into a `SessionRequest` and delegating to `AuthenticationProvider().CreateSession` [2](#0-1) .

When the LDAP authentication driver is configured, `CreateSession` performs a "simple bind" using the caller-supplied email (as DN) and password, with no validation that the password is non-empty: [3](#0-2) 

Per LDAP simple-bind semantics (RFC 4513 §5.1.2), a bind request with a valid DN and a zero-length password is defined as an "unauthenticated bind," and most LDAP servers return a success result for it *without validating any credential* — this is precisely the bug class described in the Symfony/CVE-2016-2403 advisory ("valid username + empty password → unauthenticated bind succeeds"). Because `conn.Bind(searchBaseDN, sr.Password)` is called unconditionally with `sr.Password` taken straight from the JSON request body, an attacker who submits a known/guessable email with `password: ""` can cause the bind to report success. The code then proceeds to look up the user's role via `l.FindUser(ctx, escapedEmail)` and, if that succeeds, creates a fully-privileged session record without ever having verified a credential: [4](#0-3) 

Contrast this with the local/OIDC authentication paths, which explicitly hash-compare the password (`utils.CheckPasswordHash`) and would reject an empty password against any real bcrypt hash [5](#0-4) [6](#0-5) . The LDAP driver has no equivalent guard before delegating trust entirely to the LDAP server's bind semantics.

### Impact Explanation
If exploitable against the configured LDAP server (i.e., the server does not explicitly reject unauthenticated binds, which is the historical default posture many LDAP servers had before hardening — the exact scenario the Symfony advisory addressed), an unprivileged remote attacker can obtain a valid Chainlink node session and role (Admin/Edit/Run/View, based on LDAP group membership) for any known user email without knowing their password. This is a full authentication bypass on the node's HTTP API, potentially granting Admin-level control over job runs, keys, and configuration.

### Likelihood Explanation
Likelihood depends on the LDAP server's own configuration (whether it permits unauthenticated binds), which is outside Chainlink's control. However, the Chainlink code itself performs no client-side check to prevent sending an empty-password bind request, so it is fully exposed to server-side misconfiguration/default-behavior risk — the same condition the referenced advisory exists to flag. The email/username needed can often be enumerated or is a well-known admin address (e.g., LDAP directory listings, or via the `ldap_sessions`/audit flows).

### Recommendation
In `ldapAuthenticator.CreateSession` (and `TestPassword`), explicitly reject empty passwords before calling `conn.Bind`, e.g.:
```go
if sr.Password == "" {
    return "", errors.New("password cannot be empty")
}
```
This mirrors the fix Symfony applied for CVE-2016-2403 (reject blank passwords prior to invoking LDAP bind), independent of server-side configuration.

### Proof of Concept
1. Configure the node with the LDAP authentication driver against an LDAP server that has not explicitly disabled unauthenticated/anonymous binds.
2. Send:
```
POST /sessions
Content-Type: application/json

{"email":"<known-user-email>","password":""}
```
3. `conn.Bind(searchBaseDN, "")` [7](#0-6)  succeeds as an unauthenticated bind; `FindUser` resolves the role, and a session cookie is issued for that user without any password check having occurred.

```go
func (l *ldapAuthenticator) CreateSession(ctx context.Context, sr sessions.SessionRequest) (string, error) {
	conn, err := l.ldapClient.CreateEphemeralConnection()
	if err != nil {
		return "", errors.New("unable to establish connection to LDAP server with provided URL and credentials")
	}
	defer conn.Close()

	var returnErr error

	// Attempt to LDAP Bind with user provided credentials
	escapedEmail := ldap.EscapeFilter(strings.ToLower(sr.Email))
	searchBaseDN := fmt.Sprintf("%s=%s,%s,%s", l.config.BaseUserAttr(), escapedEmail, l.config.UsersDN(), l.config.BaseDN())
	if err = conn.Bind(searchBaseDN, sr.Password); err != nil {
		l.lggr.Infof("Error binding user authentication request in LDAP Bind: %v", err)
		returnErr = errors.New("unable to log in with LDAP server. Check credentials")
	}
```
