### Title
JWT replay-guard check-then-act race allows a signed request to be authorized and processed more than once - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

### Summary
The external report describes a Checks-Effects-Interactions violation in `Migration.commit`: the state flags `proposal.isCommited`/`started` are set *after* the external, attacker-controllable call, letting a reentrant call observe the pre-commit state and re-enter, draining funds. The closest reachable analog in this Go codebase is the JWT replay-protection logic used by the internet-facing CRE/HTTP-trigger gateway path, where the "check" (has this JWT `jti` been used) and the "effect" (record the `jti` as used) are two separate, non-atomic critical sections guarded by independent lock acquisitions.

### Finding Description
`WorkflowMetadataHandler.Authorize` verifies a workflow-execution JWT, then performs replay protection using a `jwtReplayCache`: [1](#0-0) 

The replay guard itself performs the check and the record as two separate, independently-locked operations: [2](#0-1) 

`isReplay` takes an `RLock`, reads the map, and releases the lock. Only afterward — after the authorized-key lookup — does `recordUsage` take a *separate* `Lock` and write the `jti` into the cache. There is no single critical section covering "check-not-seen" + "mark-seen"; the effect (marking the JWT as used) is deferred until after other work (signer/authorized-key lookup) completes, mirroring the report's root cause where the state-changing effect (`proposal.isCommited = true`) is deferred until after other work/external interaction.

This is invoked from the gateway's HTTP trigger path via `authorizeRequest`, which is reached directly from an unprivileged client's `HandleUserTriggerRequest` call: [3](#0-2) 

Two concurrent gateway requests carrying the exact same signed JWT (same `jti`, same digest-bound payload) that arrive close together can both pass `isReplay(jti)` before either calls `recordUsage(jti)`, because the check and the write are not atomic and are separated by unrelated intervening logic (authorized-key map lookup). Both requests then proceed to be authorized and dispatched to the DON as legitimate distinct trigger requests (each has its own outer `requestID`/callback, so the existing per-`requestID` in-flight dedup in `HandleUserTriggerRequest`/`h.callbacks` — seen in the "duplicate request ID" test — does not protect against this, since that guard keys on `requestID`, not on the JWT `jti`).

The existing test suite only exercises the sequential case ("JWT replay protection" test calls `Authorize` twice back-to-back), never a concurrent/racing call, so the TOCTOU window is not covered: [4](#0-3) 

### Impact Explanation
A single validly-signed workflow-execution request (JWT) is intended to authorize exactly one execution. If the check-then-act race is won, the same signed authorization can be used to get two (or more) independent trigger executions dispatched to the DON/workflow nodes concurrently. Depending on the workflow's side effects (e.g., triggering fund-moving actions, external HTTP side effects, rate-limited or metered operations), this allows an unprivileged/underprivileged caller to bypass the "one JWT = one authorized execution" guarantee, i.e., a request-impersonation/replay-bypass condition analogous in spirit to draining/duplicating the effect of a single authorized action, as in the original Migration `commit` reentrancy where the single "commit" state was exploited to trigger multiple fund-moving effects.

### Likelihood Explanation
Exploitation requires only the ability to send the same HTTP(S) JSON-RPC request twice in quick succession to the gateway — trivially achievable by any client holding a valid signed JWT (which the client itself produced), with no privileged access needed. The race window is small (map read/write under separate locks with intervening logic), so reliable exploitation would require deliberate timing/parallel requests, but this is a realistic client-side capability, not a "malicious node/operator" scenario excluded by the rules.

### Recommendation
Make the replay check-and-record atomic: perform the "does jti exist" check and the "insert jti" write inside a single critical section (single `Lock()`/`Unlock()`), e.g. using a single `map` write with a compare-and-set semantic (`if _, exists := cache[jti]; exists { return alreadyUsed }; cache[jti] = now`) done entirely under one `Lock()`, or use `sync.Map`/`LoadOrStore` for a genuinely atomic check-and-set. Additionally, ensure `recordUsage` is called before any additional work that could be delayed/blocked (or is called unconditionally as the first authorized step) rather than being the last step of `Authorize`, so the "effect" precedes any other externally-observable interaction consistent with a CEI-safe design.

### Proof of Concept
Not executed (no filesystem/test-runner access in this session). A concrete PoC would add a test that:
1. Signs one JWT for a given request.
2. Spawns two goroutines that call `WorkflowMetadataHandler.Authorize(workflowID, tokenString, req)` concurrently (or artificially delays between `isReplay` and `recordUsage` via a hook) and asserts both return `nil` error, demonstrating the same JWT authorizing two distinct executions.

Note: I was not able to fully trace whether any additional synchronization exists higher up the call stack (e.g., a global request-level lock in `HandleUserTriggerRequest` that might serialize calls to `authorizeRequest` for the same JWT before reaching `Authorize`) due to running out of tool-call budget before reading the full `http_trigger_handler.go` file. func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}

func (h *httpTriggerHandler) authorizeRequest(ctx context.Context, workflowID string, req *jsonrpc.Request[json.RawMessage], callback handlers.Callback) (*gateway_common.AuthorizedKey, error) {
	h.lggr.Debugw("authorizing request", "workflowID", workflowID, "requestID", req.ID)
	key, err := h.workflowMetadataHandler.Authorize(workflowID, req.Auth, req)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInvalidRequest, "Auth failure: "+err.Error(), callback)
		return nil, errors.Join(errors.New("auth failure"), err)
	}
	return key, nil
}
