### Title
Insecure Logging of Sensitive Request Fields Due to Overly Narrow Redaction Blacklist - (File: core/web/router.go)

### Summary
The chainlink node's HTTP request logging middleware sanitizes request bodies and query parameters before writing them to the application log, but the redaction filter only matches keys containing the substring `"password"`. Any other sensitive field name (e.g., `secret`, `token`, `apiKey`, `accessKey`, RPC/bridge URLs embedding credentials) submitted by an authenticated API client is logged in cleartext at `Debug` level. This mirrors the reported `aws-sam-cli` `DockerBuildArgs` bug class (CWE-532): a user-supplied parameter intended to be sensitive ends up unredacted in tool/application output.

### Finding Description
`loggerFunc` in `core/web/router.go` is registered as global middleware for every route on the gin engine and logs each request's method, path, query, and body at `Debugw` level: [1](#0-0) 

The body is passed through `readBody` → `readSanitizedJSON`, which redacts only keys present in a hardcoded `blacklist` map (or containing the substring `"password"`): [2](#0-1) [3](#0-2) 

The blacklist is:
```
password, newpassword, oldpassword, current_password, new_account_password
```
It does not cover common secret-bearing field names such as `secret`, `token`, `apiKey`, `accessKey`, `clientSecret`, `privateKey`, or free-form fields that embed credentials in a URL (e.g., an RPC endpoint containing an API key, or a bridge/webhook URL with an embedded token). Any JSON body field under these names posted to any `/v2/...` endpoint (job specs, bridges, external initiators, node/chain config, keys import, etc.) is logged verbatim once `Debugw` is emitted, because `loggerFunc` wraps the entire router via `engine.Use(...)`: [4](#0-3) 

For example, node/chain RPC configuration explicitly documents URL fields (`WSURL`, `HTTPURL`) and API-key fields (`APIKey`) that can carry secrets embedded in the value: [5](#0-4) [6](#0-5) 

None of `APIKey`, `WSURL`, `HTTPURL`, or job-spec/bridge fields like `secret`/`token` match the blacklist, so if these are submitted through a JSON API request body, `readSanitizedJSON` will pass them through unmodified into the log line.

### Impact Explanation
If Debug-level logging is enabled (a supported, documented node operator setting, not a hardening default), any secret transmitted in a request body under a non-"password" key name is persisted in plaintext in the node's log output. This is analogous to the original CVE class: sensitive parameters intended to be confidential leak into logs that may be shipped to log aggregators, support bundles, or other systems with a broader audience than the original API caller — expanding the blast radius of credential exposure (e.g., RPC provider API keys, bridge/webhook tokens) beyond the node operator who submitted them.

### Likelihood Explanation
Exploitation requires the node to have Debug-level logging enabled and a caller (who already must be an authenticated API user) to submit a secret-bearing field that isn't named with "password". Because Debug logging is an operator-configurable option rather than an unlikely edge case, and secret-bearing field names in this codebase (`secret`, `token`, `APIKey`) are common in bridge, external-initiator, and node/chain-config payloads, the likelihood of a plaintext credential ending up in application logs is moderate — consistent with the CVSS `AC:H` (Debug logging must be enabled) rating on the original advisory.

### Recommendation
Expand `isBlacklisted`/`blacklist` in `core/web/router.go` beyond `"password"` substring matching to also cover `secret`, `token`, `key`, `apikey`, `accesskey`, and similar generic secret-indicating substrings, or switch to an allowlist-based logging approach for request bodies. Additionally, consider redacting URL-valued fields that may embed credentials (e.g., basic-auth userinfo or query-string API keys) rather than relying purely on key-name matching.

### Proof of Concept
1. Enable Debug-level logging on a chainlink node (`Log.Level = 'debug'`).
2. As an authenticated API user, submit a request whose JSON body includes a field not covered by the blacklist but holding a secret, e.g. `POST /v2/jobs` with a bridge/webhook task configuration containing `"token": "super-secret-value"`, or configure a chain node with `"APIKey": "super-secret-value"`.
3. Observe the node's log output: `loggerFunc`'s `Debugw` call will include the `body` field containing `"token":"super-secret-value"` (or `"APIKey":"super-secret-value"`) in cleartext, because `isBlacklisted` only matches `"password"`-like keys. [1](#0-0) [7](#0-6)

```go
func readSanitizedJSON(buf *bytes.Buffer) (string, error) {
	var dst map[string]any
	err := json.Unmarshal(buf.Bytes(), &dst)
	if err != nil {
		return "", err
	}

	cleaned := map[string]any{}
	for k, v := range dst {
		if isBlacklisted(k) {
			cleaned[k] = "*REDACTED*"
			continue
		}
		cleaned[k] = v
	}

	b, err := json.Marshal(cleaned)
	if err != nil {
		return "", err
	}
	return string(b), err
}
```

```go
// NOTE: keys must be in lowercase for case insensitive match
var blacklist = map[string]struct{}{
	"password":             {},
	"newpassword":          {},
	"oldpassword":          {},
	"current_password":     {},
	"new_account_password": {},
}

func isBlacklisted(k string) bool {
	lk := strings.ToLower(k)
	if _, ok := blacklist[lk]; ok || strings.Contains(lk, "password") {
		return true
	}
	return false
}
```
