### Title
Attacker-controlled MessageID lets one client overwrite another user's in-flight gateway callback, causing cross-user response confusion / DoS - (core/services/gateway/handlers/capabilities/handler.go)

### Summary
Similar to the Teller `commitCollateral` bug (state committed for a bid can be silently overwritten by anyone because the function never checks the existing/current state before mutating it), the gateway's `HandleLegacyUserMessage` writes into the shared `savedCallbacks` map keyed by a value fully controlled by the unprivileged HTTP caller (`msg.Body.MessageID`, derived straight from the JSON-RPC request `id`), without checking whether an entry already exists for that key.

### Finding Description
`HandleLegacyUserMessage` unconditionally does:
```go
h.mu.Lock()
h.savedCallbacks[msg.Body.MessageID] = &savedCallback{id: msg.Body.MessageID, createdAt: time.Now(), Callback: callback}
don := h.don
h.mu.Unlock()
``` [4](#0-3) 

`msg.Body.MessageID` is populated from the caller-supplied JSON-RPC `id` with no server-side uniqueness/collision check: [1](#0-0) 

Because two independent (even simultaneous) legacy user requests can specify the same `MessageID`, the second write silently replaces the first user's `savedCallback` entry in the map — exactly analogous to `commitCollateral` letting a second, unrelated caller silently replace previously committed state with no status/ownership check. When the DON node later responds with that `MessageID`, `handleWebAPITriggerMessage` looks the entry up, deletes it, and delivers the (first) node response to whichever callback is currently stored — i.e., potentially to the second (attacker's) HTTP connection instead of the original requester: [3](#0-2) 

This produces two concrete unprivileged-actor-triggerable impacts:
1. **Denial of service** — an attacker can proactively "claim" a `MessageID` before a legitimate user's identical/predictable ID request completes, overwriting the callback so the legitimate caller's HTTP request hangs until the callback-prune timeout (`CallbackMaxAgeSec`, default 120s) instead of getting a timely response.
2. **Cross-user response confusion** — since the map entry (and its associated callback / underlying HTTP connection) is overwritten, the node's eventual response for the original request can be delivered into the attacker's callback instead, and vice versa, depending on race timing.

### Impact Explanation
This directly matches the "unauthorized modification of another party's already-submitted/committed state without any ownership or status check" bug class from the report. It can cause response misdelivery across independent user sessions in a gateway-facing, unprivileged code path, and enables trivial denial-of-service against other gateway users by ID squatting.

### Likelihood Explanation
Likelihood is moderate: an attacker needs to guess or otherwise predict/reuse another concurrent caller's `MessageID` value at just the right time window before the legitimate response arrives. Some deployments/clients may use low-entropy or predictable IDs (e.g., sequential counters), which raises the practical likelihood. No authentication or special privilege beyond normal HTTP access to the gateway's `/user` endpoint is required — it is reachable by any external, unprivileged client.

### Recommendation
Before inserting into `savedCallbacks`, check whether an entry for `msg.Body.MessageID` already exists and, if so, reject the request (e.g., return a "duplicate/in-flight message ID" error) instead of silently overwriting it. Alternatively, generate/derive the map key server-side (e.g., combine the client ID with a gateway-generated nonce, or hash it with a per-connection/session identifier) rather than trusting the raw client-supplied `MessageID` as a global map key.

### Proof of Concept
1. Client A sends a legacy user request to the gateway's `/user` endpoint with `MessageID = "X"`. `HandleLegacyUserMessage` stores `savedCallbacks["X"] = callbackA` and forwards the request to DON nodes.
2. Before the DON node responds, Client B sends another legacy request also using `MessageID = "X"`. `HandleLegacyUserMessage` overwrites `savedCallbacks["X"] = callbackB` with no check for the existing entry, and forwards its own request to DON nodes.
3. When a DON node responds with `MessageID = "X"` (matching Client A's original in-flight request), `handleWebAPITriggerMessage` looks up `savedCallbacks["X"]`, finds `callbackB`, deletes the entry, and delivers the response meant for Client A to Client B's HTTP connection.
4. Client A's request instead times out and remains unresolved until it is later expired/pruned by `pruneCallbacks`, or (depending on race timing) may instead receive Client B's response.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageID]
	delete(h.savedCallbacks, msg.Body.MessageID)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JSONRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
