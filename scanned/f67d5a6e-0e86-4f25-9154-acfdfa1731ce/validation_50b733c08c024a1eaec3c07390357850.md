### Title
Governance approval/support thresholds are computed against **live, mutable `TotalIssuance`**, allowing a large holder to reduce the denominator (via `pallet_balances::Pallet::burn`) and artificially lower the bar needed to pass a referendum - ([File: substrate/frame/conviction-voting/src/types.rs])

### Summary
The Ajna report shows that computing a voting threshold against the *current* token supply (rather than a snapshot taken at proposal creation) lets an attacker shrink the supply mid-vote to lower the bar for passing. The same structural pattern exists in Polkadot/Substrate's OpenGov stack: `pallet-conviction-voting`'s `Tally::support()` divides the aye-capital by a `Total: Get<Votes>` type that resolves to the **live** `TotalIssuance` of the native currency, and this value is re-read continuously by `pallet-referenda` while a referendum is deciding/confirming.

### Finding Description
`Tally::support` computes support as a fraction of the configured `Total`: [1](#0-0) 

In the reference runtime configuration, `Total` (via `MaxTurnout`) is bound to `frame_support::traits::TotalIssuanceOf<Balances, Self::AccountId>` — i.e., the pallet-balances `TotalIssuance` storage value read live, not a snapshot from proposal-submission time: [2](#0-1) 

`pallet-referenda` re-evaluates `support`/`approval` against this live total on essentially every block while a referendum is in the deciding phase, to compute when/whether it is "passing" and to schedule the alarm that flips it into (or out of) the confirmation period: [3](#0-2) [4](#0-3) 

`pallet-balances` exposes `TotalIssuance` as an adjustable, live value that shrinks whenever tokens are destroyed (e.g. via a self-burn dispatchable or `Unbalanced::set_total_issuance`/imbalance drop paths), analogous to `AjnaToken` inheriting `ERC20Burnable`: [5](#0-4) 

Because `support_needed.passing(x, tally.support(id))` (in `is_passing`) recomputes the percentage every time using this live `TotalIssuance`, an account holding a large fraction of the free-floating (non-locked-in-vote) supply could burn part of its *own, unvoted* balance to shrink `TotalIssuance`. This raises the resulting `support` percentage for a given (fixed) `aye`-capital total without adding a single additional aye vote, potentially pushing a borderline referendum from "not passing" into "passing" and triggering (or shortening) its confirmation period.

This mirrors the Ajna root cause precisely: `_getSliceOfNonTreasury()` used `IERC20(ajnaTokenAddress).totalSupply()` live rather than a snapshot, letting a holder burn tokens to lower the required vote count.

### Impact Explanation
If exploitable, an attacker with a very large fraction of the freely circulating (unlocked) native token could:
1. Vote aye on a borderline referendum (e.g. spending track) with only enough capital to be *close* to the support floor.
2. Burn a large amount of their own uninvolved balance right before/during the decision or confirmation period.
3. Cause `Tally::support()` to spike because the same aye-capital is now divided by a smaller `TotalIssuance`, satisfying `min_support` at that point in the track's decay curve, letting the referendum enter/stay in its confirmation window and ultimately execute (e.g., approve a Treasury spend) with genuinely less real backing than the track's curve was designed to require.

This affects protocol-level governance integrity (Treasury spends, root-level referenda) — the same asset class of impact as the original Ajna Medium finding.

### Likelihood Explanation
Likelihood is low-to-moderate and highly assumption-dependent, similar to the original finding being downgraded from High to Medium:
- It requires the attacker to control (and be willing to permanently destroy) a very large amount of the native token (DOT/KSM/etc.) relative to circulating supply — economically costly, unlike burning a governance token whose destruction may be cheaper relative to the treasury upside.
- OpenGov's `min_support`/`min_approval` **curves already decay over the decision period** (see `substrate/frame/referenda/src/lib.rs` `decision_time`/`is_passing`, and the `Curve` definitions in track configs such as `cumulus/parachains/runtimes/assets/asset-hub-westend/src/governance/tracks.rs`), which was explicitly designed to account for changing conditions (including supply changes) over time — this is analogous to the Ajna judge's own reasoning that "it is within the design of the grant system that the threshold is computed at the end of the voting period to account for potential parallel proposals and changes in the external supply."
- The `confirm_period` mechanism requires the passing condition to be sustained continuously, meaning a one-off burn spike is not sufficient; the attacker would need to keep the reduced-issuance state (i.e., keep the burned tokens burned) for the whole confirmation window, which is a real, permanent, and visible economic cost, further reducing practical likelihood versus the Ajna case where burns are cheap/reversible-in-intent (attacker just forfeits tokens they'd rather not use anyway).

### Recommendation
- Consider whether `min_support`/`min_approval` should be computed against a `TotalIssuance` value snapshotted at referendum submission (or another manipulation-resistant baseline, e.g. issuance at the start of the deciding phase) rather than a live-read value that can be moved by any large holder mid-vote.
- Alternatively, document/confirm (if not already) that OpenGov's decaying support/approval curves are an intentional, accepted mitigation for this exact class of issue (as Ajna's team ultimately concluded), and evaluate whether the decay rate for high-value tracks (root, treasurer, big spender) gives enough margin against a plausible worst-case issuance reduction.

### Proof of Concept
A conceptual PoC (illustrative, not exhaustively verified against exact extrinsic names/weights due to tool/time limits):
1. Deploy/observe a `pallet-referenda` track (e.g. `treasurer`) whose `min_support` curve is currently just above the floor needed to pass, with `Tally.support` computed via `pallet-conviction-voting`'s `Tally::support()` against live `TotalIssuanceOf<Balances, AccountId>`.
2. Attacker votes `aye` on a proposal with capital `C`, giving `support = C / TotalIssuance` slightly below `min_support` at the current decision-period position.
3. Attacker calls the balances pallet's self-burn dispatchable (or otherwise destroys) a large amount of their own free, unvoted balance `B`, reducing `TotalIssuance` to `TotalIssuance - B`.
4. On the next block, `Referenda::nudge_referendum`/`begin_block` re-evaluates `is_passing` via `decision_time`, and `support = C / (TotalIssuance - B)` now exceeds `min_support`, moving the referendum into (or keeping it in) the confirmation period.
5. If the attacker sustains the reduced issuance through the confirm period, the referendum is approved and its call is scheduled for dispatch — despite genuine backing (`C`) never having grown.

Note: I was unable to fully confirm the exact public dispatchable name/index for a permissionless self-burn in `pallet-balances` within the available search iterations (only its presence was located via grep, not its full definition), so the "attacker burns own free balance" step should be verified against the current `pallet_balances::Call` variants before treating this as fully confirmed. This is flagged as an open verification item rather than a certainty.

```rust
	/// Determine the point at which a referendum will be accepted, move into confirmation with the
	/// given `tally` or end with rejection (whichever happens sooner).
	fn decision_time(
		deciding: &DecidingStatusOf<T, I>,
		tally: &T::Tally,
		track_id: TrackIdOf<T, I>,
		track: &TrackInfoOf<T, I>,
	) -> BlockNumberFor<T, I> {
		deciding.confirming.unwrap_or_else(|| {
			// Set alarm to the point where the current voting would make it pass.
			let approval = tally.approval(track_id);
			let support = tally.support(track_id);
			let until_approval = track.min_approval.delay(approval);
			let until_support = track.min_support.delay(support);
			let offset = until_support.max(until_approval);
			deciding.since.saturating_add(offset.mul_ceil(track.decision_period))
		})
	}
```

```rust
	/// Determine whether the given `tally` would result in a referendum passing at `elapsed` blocks
	/// into a total decision `period`, given the two curves for `support_needed` and
	/// `approval_needed`.
	fn is_passing(
		tally: &T::Tally,
		elapsed: BlockNumberFor<T, I>,
		period: BlockNumberFor<T, I>,
		support_needed: &Curve,
		approval_needed: &Curve,
		id: TrackIdOf<T, I>,
	) -> bool {
		let x = Perbill::from_rational(elapsed.min(period), period);
		support_needed.passing(x, tally.support(id)) &&
			approval_needed.passing(x, tally.approval(id))
	}
```

```rust
pub fn set_total_issuance<T, AccountId>()

	T: Unbalanced<AccountId>,

		assert_eq!(T::total_issuance(), T::minimum_balance() - 1.into());
	}
```
