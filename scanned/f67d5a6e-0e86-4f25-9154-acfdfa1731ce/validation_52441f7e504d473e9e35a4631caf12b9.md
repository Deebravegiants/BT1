### Title
Unbounded `drain_prefix` over attacker-inflatable `Attribute`/`ItemMetadataOf` storage makes NFT collection `destroy` permanently uncallable - (File: substrate/frame/nfts/src/features/create_delete_collection.rs)

### Summary
`set_attribute` lets any unprivileged, non-collection-owner user (an item owner, or an `Account`-namespace delegate) cheaply create an unbounded number of `Attribute` entries tied to a collection they do not control. `do_destroy_collection` drains *all* attributes (and item metadata) in a single unbounded loop with no pagination limit, unlike the bounded `ItemConfigOf::clear_prefix`, so an attacker can inflate the collection's `attributes` counter to a size whose destroy weight exceeds the runtime's max block/extrinsic weight, permanently preventing the honest collection owner from ever calling `destroy`.

### Finding Description
`set_attribute` (`substrate/frame/nfts/src/lib.rs:1429`) dispatches to `do_set_attribute` (`substrate/frame/nfts/src/features/attributes.rs:50`). For the `ItemOwner` namespace the depositor is the caller (the item owner) themselves [1](#0-0) , and for the `Account(AccountId)` namespace it is the pre-approved delegate [2](#0-1) . Neither namespace requires the collection owner's cooperation - only item ownership (which can be obtained via a public/permissionless `mint`) or a delegate approval granted by an item owner via `approve_item_attributes`. Each call increments `Collection::attributes` with no visible cap on the total number of attributes a collection can accumulate [3](#0-2) .

When the collection owner later tries to reclaim their deposit via `destroy`, `do_destroy_collection` performs:
```
for (_, metadata) in ItemMetadataOf::<T, I>::drain_prefix(&collection) { ... }
...
for (_, (_, deposit)) in Attribute::<T, I>::drain_prefix((&collection,)) { ... }
``` [4](#0-3) 
Both `drain_prefix` calls have **no limit argument** and will iterate over every matching entry in a single call, unlike the adjacent `ItemConfigOf::<T, I>::clear_prefix(&collection, witness.item_configs, None)` which is explicitly bounded by the witness count [5](#0-4) . The `destroy` extrinsic's declared weight is computed from the witness values (`T::WeightInfo::destroy(item_metadatas, item_configs, attributes)`) [6](#0-5) , and the witness must exactly match the real `attributes`/`item_metadatas` counters or the call fails with `BadWitness` [7](#0-6) . `destroy()` requires `items == 0` but does not require the caller to have cleared attributes individually first - `do_destroy_collection` drains and unreserves every attribute's deposit regardless of who deposited it, so no per-attribute permission check (`is_valid_namespace`) blocks the drain. The only obstacle is weight: if the attacker inflates `attributes` large enough, the correctly-witnessed `destroy` call's weight will exceed the chain's max extrinsic/block weight, and the extrinsic can never be included in any block - a permanent denial of the only user-facing cleanup path.

### Impact Explanation
This permanently locks the collection owner's `owner_deposit`/`CollectionDeposit` reserved balance (and any other still-reserved metadata/attribute deposits) because `destroy` - the only mechanism to reclaim the collection deposit and remove the `Collection`/`CollectionConfigOf` storage - becomes permanently non-executable once `attributes` exceeds the block-weight-derived threshold. This matches the "Permanent asset lock or state corruption that blocks transfers" impact class, since collection-level storage and reserved funds become permanently stuck.

### Likelihood Explanation
Preconditions: the collection must allow either public/permissionless minting (a common, legitimate collection-owner configuration) so the attacker can become an item owner, or an item owner must grant an `Account`-namespace approval (`approve_item_attributes`) to the attacker - the attacker does not need any privileged role. Once an item is owned/approved, the attacker can call `set_attribute` repeatedly with minimal-size keys/values, paying only `AttributeDepositBase + DepositPerByte*(len)` per attribute, and is not require to keep the item alive (burn does not remove `ItemOwner`-namespace attributes, as shown by the pallet's own tests which keep attributes present after `burn` and require separate `clear_attribute` calls). I could not verify from available code whether there is a chain-wide cap on the number of attributes a single collection can hold, nor did I confirm the concrete `AttributeDepositBase`/`DepositPerByte`/max-block-weight values used in production runtimes (e.g., Asset Hub) needed to compute the exact number of attributes required to exceed the weight limit - this affects how expensive the griefing is in absolute terms, though the mechanism itself (unbounded `drain_prefix` with no limit, contrasted with the bounded `clear_prefix`) is a genuine, exploitable asymmetry in the code as written.

### Recommendation
Bound the `Attribute` and `ItemMetadataOf` drains in `do_destroy_collection` the same way `ItemConfigOf` is bounded - i.e., use a limited `clear_prefix`/paginated draining keyed off `witness.attributes` / `witness.item_metadatas`, and allow/require `destroy` to be called multiple times (or a dedicated `destroy_attributes`/`destroy_metadatas` step) until the counters reach zero, so weight per call stays within block limits regardless of how many attributes an unprivileged actor accumulated. Additionally consider imposing a maximum attribute count per collection (or per item) enforced in `do_set_attribute`.

### Proof of Concept
Rust integration test plan (in `substrate/frame/nfts/src/tests.rs`):
1. `force_create` a collection with public minting enabled; have attacker account mint many items into itself (or have an honest owner-minted item, then `approve_item_attributes` to the attacker).
2. Attacker calls `set_attribute` with `AttributeNamespace::ItemOwner` (or `Account(attacker)`) repeatedly with minimal `key`/`value` sizes across many items until `Collection::<Test>::get(0).unwrap().attributes` is very large (e.g., tens of thousands), funding the attacker account sufficiently for the deposits.
3. Burn all items (`items == 0`).
4. Compute the real `DestroyWitness` via `get_destroy_witness` and call `Nfts::destroy` with the correct witness from the collection owner's origin.
5. Assert that `T::WeightInfo::destroy(...)` for this witness exceeds `<Test as frame_system::Config>::BlockWeights::get().max_block` (or the relevant `max_extrinsic` limit), demonstrating the extrinsic is uncallable in production, and that `Collection::<Test>::contains_key(0)` remains true forever (deposit permanently locked), while an equivalent scenario with a small, bounded attribute count succeeds.
