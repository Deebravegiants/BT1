### Title
Double-application of pending storage diff to `ContractInfo` via `apply_pending_storage_changes` corrupts persisted deposit accounting - ([File: substrate/frame/revive/src/metering/mod.rs])

### Summary
`FrameMeter::apply_pending_storage_changes` mutates a contract's `ContractInfo` (storage_bytes/items and their deposit fields) from the frame's still-`Alive` pending diff so that a freshly spawned child frame can see the parent's not-yet-finalized state, but it does **not** consume or reset that diff. When the parent frame later calls `FrameMeter::finalize` (which invokes `finalize_own_contributions`), the *same* diff is applied to the *same* `ContractInfo` a second time, double-incrementing `storage_bytes`, `storage_items`, `storage_byte_deposit`, and `storage_item_deposit`.

### Finding Description
`apply_pending_changes_to_contract` explicitly documents that, unlike the sibling method `bank_pending_changes`, it "does not consume the pending diff, allowing the meter to continue tracking changes after the nested call returns": [1](#0-0) 

Compare this with `bank_pending_changes`, which explicitly resets `own_contribution` to `Contribution::Alive(Default::default())` after applying the diff to `info` in order to avoid exactly this kind of re-application: [2](#0-1) 

`Diff::update_contract` is not idempotent with respect to `info`: each invocation unconditionally does `info.storage_bytes = info.storage_bytes.saturating_add(bytes_added).saturating_sub(bytes_removed)` and the analogous updates for `storage_items`, `storage_byte_deposit`, `storage_item_deposit`: [3](#0-2) 

`FrameMeter::apply_pending_storage_changes` (public wrapper) is called by the executor before spawning a nested call so the child can "see" the parent's uncommitted pending deposit state, per the comment referencing contract-issues#213: [4](#0-3) 

Later, when the parent frame concludes (independent of whether the child reverted or not), `FrameMeter::finalize` calls `finalize_own_contributions`, which again runs `self.own_contribution.update_contract(info)` on the *unreset* `Alive(diff)` and only afterwards flips the contribution to `Checked(deposit)`: [5](#0-4) [6](#0-5) 

Because the diff object is unchanged between the two calls, if both calls operate on the same `ContractInfo` instance (which is the entire purpose of `apply_pending_storage_changes` — to update the live info seen by the rest of the call stack), the byte/item counters and their associated deposit fields recorded on `ContractInfo` are incremented twice for a single real storage change. This diverges the meter's *returned* charge (used for the immediate `Charge`/`Refund` transfer, which is largely diff-derived and not itself doubled for pure additions) from the *persisted* `ContractInfo` bookkeeping fields (`storage_byte_deposit`, `storage_item_deposit`, `storage_bytes`, `storage_items`), which permanently retain double the actual value. These persisted fields are the basis for all future refund-ratio calculations (`ratio = bytes_removed / info.storage_bytes`, refund = `ratio * info.storage_byte_deposit`) and for full-refund-on-termination logic elsewhere in the pallet. An inflated `storage_byte_deposit`/`storage_item_deposit` on a contract's `ContractInfo` means a subsequent full refund (e.g. on contract termination) can pay out more than was ever actually collected from the depositor, and inflated `storage_bytes`/`storage_items` denominators corrupt the pro-rata refund ratio for future partial storage removals — both are deposit-accounting/refund-integrity bugs distinct from the intended one-charge-per-real-byte invariant.

### Impact Explanation
The bug causes the persisted per-contract storage accounting (`ContractInfo::storage_byte_deposit`/`storage_item_deposit`/`storage_bytes`/`storage_items`) to diverge from the actual on-chain storage footprint and from the amount actually held/reserved from the depositor. This is exactly the "storage-deposit metering asymmetry" scoped in the question: subsequent refund calculations (partial refunds pro-rated against `info.storage_bytes`, or full refunds on contract termination based on `info.storage_byte_deposit`) will be computed against corrupted, doubled baseline values, enabling a depositor/attacker-controlled contract to eventually receive a refund exceeding the amount that was truly deposited for its storage usage — an underpayment for real storage usage from the protocol's perspective.

### Likelihood Explanation
This requires only unprivileged capability already assumed by the pallet-revive design: an attacker deploys a parent contract `P` that performs a storage write (invoking `record_contract_storage_changes`), then makes a cross-contract call to a controlled child `C` (triggering `apply_pending_storage_changes` before the nested frame is created), after which `P`'s frame eventually finalizes (`finalize`/`finalize_own_contributions`) with its `own_contribution` diff untouched by the intervening peek call. No special origin, signature, or governance access is needed — a normal `call`/`instantiate` extrinsic against two attacker-deployed contracts suffices, and the sequence is fully reproducible on demand.

### Recommendation
Make `apply_pending_storage_changes` consistent with `bank_pending_storage_changes`: after applying the diff to `info` for child visibility, either (a) reset `own_contribution` to `Alive(Default::default())` immediately (mirroring `bank_pending_changes`), tracking any further writes in a fresh diff, and pushing the already-computed deposit into `charges` immediately (as `bank_pending_changes` does), or (b) if the pending-peek must remain non-committing, revert the `info` mutation performed by the peek before `finalize_own_contributions` runs so the final diff application starts from a clean baseline. In either case, `Diff::update_contract` must never be applied twice against the same `ContractInfo` for the same accumulated diff.

### Proof of Concept
Integration test in `substrate/frame/revive`:
1. Deploy parent contract `P` with a storage-writing entry point that (a) writes N bytes to its own storage (`set_storage`), (b) calls child contract `C` via `call`, (c) after the call returns, does nothing further and returns success.
2. Deploy child contract `C` whose entry point simply returns success (no storage change needed to trigger the bug — the double-application happens on `P`'s own diff regardless of `C`'s behavior, since `apply_pending_storage_changes` is invoked purely because a nested frame is being created).
3. Execute `P`'s entry point via `Contracts::call`/`Pallet::bare_call`.
4. After execution, read `ContractInfoOf::<Test>::get(&p_address)` and assert `storage_byte_deposit`/`storage_bytes` equal `N * DepositPerByte` / `N` (single application), not `2 * N * DepositPerByte` / `2 * N`.
5. Additionally assert that `NativeDepositOf`/hold balance moved from the depositor equals exactly `N * DepositPerByte` (the true one-time charge), not double.
6. As a follow-up scenario, have `P` later remove all N bytes in a second call and assert the refund received equals the full original deposit (not half of it, which would happen if the stored baseline were inflated to `2N`).

	/// Apply pending storage changes to a ContractInfo without finalizing the meter.
	///
	/// This is used before creating a nested frame to ensure the child frame can see
	/// the parent's pending storage changes when calculating refunds.
	///
	/// Unlike [`Self::finalize_own_contributions`], this does not consume the pending diff,
	/// allowing the meter to continue tracking changes after the nested call returns.
	pub fn apply_pending_changes_to_contract(&self, info: &mut ContractInfo<T>) {
		if let Contribution::Alive(diff) = &self.own_contribution {
			// Apply the diff to update the ContractInfo's storage deposit fields.
			// We don't care about the return value (the deposit amount) here,
			// we just want to update the ContractInfo so child frames can see it.
			let _ = diff.update_contract::<T>(Some(info));
		}
	}

	/// Apply the pending diff to `info` and push its deposit as a final charge, then reset
	/// `own_contribution` so finalize does not apply it a second time.
	pub fn bank_pending_changes(&mut self, contract: T::AccountId, info: &mut ContractInfo<T>) {
		if let Contribution::Alive(_) = &self.own_contribution {
			let deposit = self.own_contribution.update_contract(Some(info));
			self.own_contribution = Contribution::Alive(Default::default());
			if !deposit.is_zero() {
				self.charge_deposit(contract, deposit);
			}
		} else {
			debug_assert!(
				false,
				"on-stack ancestor frames have not finalized yet, so own_contribution \
				 should be Alive when banked; qed",
			);
		}
	}
