### Title
ERC-20 `approve()` front-running / multiple-withdrawal race condition in `pallet-assets` precompile - (File: `substrate/frame/assets/precompiles/src/lib.rs`)

### Summary
The `pallet-assets` ERC-20 precompile's `approve` and `permit` functions implement standard ERC-20 "set" semantics (`approve(spender, N)` overwrites the allowance to exactly `N`), which reproduces the exact same "Multiple Withdrawal Attack" race condition described in the referenced Foundation `FETH` report. The implementation explicitly acknowledges this in an inline comment without providing `increaseAllowance`/`decreaseAllowance` mitigations.

### Finding Description
The `approve` function reads the `current` allowance, cancels it, and re-approves the `new_amount`, matching ERC-20 spec behavior [1](#0-0) . The code contains an explicit acknowledgment of the unmitigated race condition:

> "NOTE: This does not mitigate the well-known ERC-20 approve front-running race condition. Callers concerned about this should approve to 0 first, or use increaseAllowance/decreaseAllowance if available." [2](#0-1) 

No `increaseAllowance`/`decreaseAllowance` functions exist anywhere in the precompile interface — only `approve`, `transferFrom`, and `permit` [3](#0-2) . The same "beware of transaction ordering" warning is duplicated in the vendored OpenZeppelin `IERC20.sol` interface comment used as reference [4](#0-3) , confirming the developers are aware this is the classic OpenZeppelin-documented risk but chose not to add mitigating functions.

This mirrors the underlying `pallet-assets` native dispatchable `approve_transfer`, which is documented as *additive* ("If there is already an approval in place, then this acts additively") [5](#0-4) , making the underlying primitive itself vulnerable to the classic double-spend-via-reordering pattern that the precompile's cancel-then-set wrapper only partially addresses (it fixes ERC-20 compliance per `prdoc/stable2606/pr_11279.prdoc` but explicitly does not fix the race) [6](#0-5) .

### Impact Explanation
A malicious or compromised `spender` who has been granted a non-zero allowance by an `owner` can front-run the owner's subsequent `approve(spender, newAmount)` call by submitting a `transferFrom` using the old allowance. If the transferFrom lands before the new approve is included, the spender can spend up to `old_allowance + new_allowance` in total rather than just `new_allowance`, exceeding the owner's intended authorization limit. This is a fund-safety issue for any owner who changes an existing non-zero allowance to a spender.

### Likelihood Explanation
Realistic likelihood is low-to-moderate and matches the original report's own characterization ("poses a limited risk in specific situations"). It requires: (1) the owner already granted a non-zero allowance to a spender, (2) the spender or an entity observing pending extrinsics acts adversarially by submitting `transferFrom` ahead of the owner's allowance-update transaction, and (3) block/extrinsic ordering allows such reordering (transaction pool visibility in Substrate-based chains, similar to Ethereum mempool visibility, makes this feasible for parachain block producers/collators or MEV-style actors). No privileged or trusted role is required — only an unprivileged spender account that was previously approved.

### Recommendation
Add non-standard `increaseAllowance(spender, addedValue)` and `decreaseAllowance(spender, subtractedValue)` functions to the ERC-20 precompile interface (`IERC20.sol`) and implementation in `substrate/frame/assets/precompiles/src/lib.rs`, mirroring the OpenZeppelin mitigation referenced in the original report. This lets callers atomically adjust allowances without a set-to-arbitrary-value race window.

### Proof of Concept
1. Owner calls `approve(spender, 100)` via the precompile — `Approvals` allowance becomes 100 [7](#0-6) .
2. Owner later decides to reduce trust and calls `approve(spender, 10)` intending to leave only 10 spendable.
3. Spender observes the pending `approve(spender, 10)` extrinsic in the transaction pool and submits `transferFrom(owner, attacker, 100)` first.
4. If the spender's `transferFrom` is included before the owner's new `approve`, the spender drains the full original 100, and then the new `approve(spender, 10)` still executes afterward (cancel + re-approve, per lines 396-418), granting the spender an additional 10 — for a total of 110 spent versus the owner's intended final cap of 10. [8](#0-7)

	/// Execute the approve call.
	///
	/// Implements ERC-20 set semantics: `approve(spender, N)` sets the allowance to exactly `N`
	/// rather than adding to it. When overwriting a non-zero allowance, the existing approval is
	/// cancelled first so the new value replaces (not accumulates with) the old one.
	///
	/// `call.value > Balance::MAX` (the `type(uint256).max` "infinite allowance" idiom)
	/// saturates the stored allowance at `Balance::MAX`. The `Approval` event carries the
	/// raw `call.value`.
	fn approve(
		asset_id: <Runtime as Config<Instance>>::AssetId,
		call: &IERC20::approveCall,
		env: &mut impl Ext<T = Runtime>,
	) -> Result<Vec<u8>, Error> {
		use frame_support::traits::fungibles::approvals::Inspect as ApprovalsInspect;

		// Reserve worst-case gas upfront, then refund the unused portion.
		let worst_case = <Runtime as Config<Instance>>::WeightInfo::allowance()
			.saturating_add(<Runtime as Config<Instance>>::WeightInfo::cancel_approval())
			.saturating_add(<Runtime as Config<Instance>>::WeightInfo::approve_transfer());
		let charged = env.charge(worst_case)?;

		let owner = Self::caller(env)?;
		let owner_account =
			<Runtime as pallet_revive::Config>::AddressMapper::to_account_id(&owner);
		let spender: H160 = call.spender.into_array().into();
		let spender_account = env.to_account_id(&spender);
		// Saturate: `type(uint256).max` is the standard "infinite allowance" idiom and must
		// not revert at the conversion boundary.
		let new_amount: <Runtime as Config<Instance>>::Balance = call.value.unique_saturated_into();

		let current = pallet_assets::Pallet::<Runtime, Instance>::allowance(
			asset_id.clone(),
			&owner_account,
			&spender_account,
		);

		let actual_weight;
		if new_amount.is_zero() {
			if !current.is_zero() {
				// Revoke: use the pallet's cancel logic to remove the approval and
				// unreserve the deposit.
				pallet_assets::Pallet::<Runtime, Instance>::do_cancel_approval(
					&asset_id,
					&owner_account,
					&spender_account,
				)?;
				actual_weight = <Runtime as Config<Instance>>::WeightInfo::allowance()
					.saturating_add(<Runtime as Config<Instance>>::WeightInfo::cancel_approval());
			} else {
				// 0→0 no-op: only the allowance read was needed.
				actual_weight = <Runtime as Config<Instance>>::WeightInfo::allowance();
			}
		} else {
			// If there's an existing non-zero allowance, cancel it first so we
			// overwrite (not accumulate) — matching ERC-20 spec semantics.
			// NOTE: This does not mitigate the well-known ERC-20 approve front-running
			// race condition. Callers concerned about this should approve to 0 first,
			// or use increaseAllowance/decreaseAllowance if available.
			if !current.is_zero() {
				pallet_assets::Pallet::<Runtime, Instance>::do_cancel_approval(
					&asset_id,
					&owner_account,
					&spender_account,
				)?;
				actual_weight = worst_case;
			} else {
				actual_weight = <Runtime as Config<Instance>>::WeightInfo::allowance()
					.saturating_add(<Runtime as Config<Instance>>::WeightInfo::approve_transfer());
			}
			pallet_assets::Pallet::<Runtime, Instance>::do_approve_transfer(
				asset_id,
				&owner_account,
				&spender_account,
				new_amount,
			)?;
		}
