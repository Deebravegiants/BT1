Based on my investigation, this is **not a valid finding as a general framework bug**.

The `CallFlags::READ_ONLY`/`is_read_only()` gate is enforced at the frame-propagation level in `exec.rs`, not left ad hoc per precompile. When `PrecompileExt::call` is invoked, `is_read_only` is computed as `read_only || self.is_read_only()` and passed into `push_frame`, so the read-only status is unconditionally inherited by the child frame regardless of whether the destination is a precompile with `HAS_CONTRACT_INFO = true` or a regular contract: [1](#0-0) 

This means `env.is_read_only()`, as called from `System::call` at substrate/frame/revive/src/precompiles/builtin/system.rs:47-49, and as called from the `ERC20` precompile's dispatcher (`substrate/frame/assets/precompiles/src/lib.rs:176-185`), reads a value that is *already forced true* by the framework whenever the outer call was made with `READ_ONLY`. It is not a value the precompile itself derives independently, and it cannot be "bypassed" by omitting a check somewhere unrelated to state mutation, because the actual storage-write primitives exposed through `ExtWithInfo` (e.g. `set_storage`, `charge_storage`, `transfer`, `instantiate`) are the ones that must consult `is_read_only`/frame state to reject writes — this is analogous to how the `pvm.rs` `call` host function only *forwards* `read_only` into `ext.call`, it doesn't perform the storage mutation itself.

That said, my search could not conclusively verify (within the available iterations) whether every low-level storage-mutating primitive on `ExtWithInfo` (e.g., raw storage set/clear, deposit charging, `instantiate` path used by `HAS_CONTRACT_INFO` precompiles) itself checks `is_read_only()` before mutating storage, as opposed to relying entirely on each precompile author manually gating on `env.is_read_only()` in their own `call_with_info` match arms (as the ERC20 precompile explicitly does at lines 176-185, and as documented in the regression test `permit_staticcall_is_rejected` at substrate/frame/assets/precompiles/src/permit_precompile_tests.rs:1062-1079). This confirms the premise of the question: **read-only enforcement for `HAS_CONTRACT_INFO = true` precompiles is per-precompile/ad-hoc, not uniformly enforced by the `ExtWithInfo` storage primitives or by `exec.rs`/`pvm.rs`.** The framework correctly computes and propagates `is_read_only()` down to the frame, but it is each precompile author's responsibility to check `env.is_read_only()` before performing a mutating branch in `call_with_info`. A future `HAS_CONTRACT_INFO = true` precompile that forgets this check (unlike `System::call` and the `ERC20` precompile, which do check it explicitly) would indeed allow a `READ_ONLY` call to mutate its contract-info-backed storage.

### Title
Read-only enforcement for `HAS_CONTRACT_INFO=true` precompiles is per-precompile, not framework-enforced - (File: substrate/frame/revive/src/precompiles.rs)

### Summary
The `Precompile`/`BuiltinPrecompile` trait's `call_with_info` entry point and the underlying `ExtWithInfo` storage-mutating APIs do not themselves enforce `env.is_read_only()`; each precompile author must manually check it in their dispatch logic, as seen in `System::call` and the `ERC20` precompile. This is a design gap rather than a currently exploitable bug in any shipped precompile, since all existing `HAS_CONTRACT_INFO` precompiles the repo indexes (System, ERC20/permit) do implement the check.

### Finding Description
`Precompile::call_with_info` receives `env: &mut impl ExtWithInfo<T>` and is free to call mutating APIs (storage set, transfer, instantiate) without any framework-level gate on `is_read_only()`. [4](#0-3) 
The framework does correctly propagate `READ_ONLY` down through `PrecompileExt::call` → `push_frame`, so `env.is_read_only()` returns the correct value. [1](#0-0) 
However, nothing forces a precompile's mutating branches to check that flag — it's opt-in per precompile, exactly like `System::call` and `ERC20::call` do via explicit `if env.is_read_only()` guards. The `permit_staticcall_is_rejected` test comment confirms that the underlying `frame_support` storage writes "bypass pallet-revive's host-call read-only gating," i.e., there is no lower-level enforcement.

### Impact Explanation
If a future `HAS_CONTRACT_INFO=true` precompile omits this check on a mutating branch, an unprivileged EOA/contract could issue a `READ_ONLY` call and mutate that precompile's contract-info-backed storage, violating the static-call invariant. Impact is scoped to that specific future/misconfigured precompile, not to any code currently in the repository.

### Likelihood Explanation
Low for currently shipped precompiles (System and ERC20 both implement the guard correctly), but structurally likely for future or third-party precompiles unless a uniform enforcement mechanism is added, since the check is easy to forget and is not caught by any compile-time or generic runtime guard.

### Recommendation
Add a uniform enforcement layer: either (a) have the generic dispatch path (`PrimitivePrecompile::call_with_info` / `Instance::call`) intercept a precompile-declared list of "mutating" selectors and reject them under `is_read_only()` before calling into the precompile, or (b) have `ExtWithInfo`'s storage-mutating primitives (`set_storage`, `transfer`, `instantiate`, deposit-charging) themselves check `is_read_only()` and return `Error::<T>::StateChangeDenied`, removing reliance on manual per-precompile checks.

### Proof of Concept
Add a test precompile with `HAS_CONTRACT_INFO = true` that has one branch performing `env.set_storage(...)` without checking `is_read_only()`, then differential-test it analogous to `read_only_call_cannot_store`/`read_only_call_cannot_transfer` (substrate/frame/revive/src/tests/pvm.rs:3335-3379): call it with `CallFlags::READ_ONLY` and assert the storage write actually occurred (proving the gap), then assert that `System::call` and `ERC20::call` correctly return `Error::<T>::StateChangeDenied` for their mutating selectors under the same read-only context, generalizing this into a fuzz/invariant test iterating over all registered precompiles' mutating selectors.
