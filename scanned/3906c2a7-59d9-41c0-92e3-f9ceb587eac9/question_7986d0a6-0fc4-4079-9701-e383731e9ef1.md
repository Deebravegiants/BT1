Target: `SaltManager.getCachedSalt`/`refresh` (packages/intents-sdk/src/intents/salt-manager.ts) combined with `IntentPayloadBuilder.build`/`buildWithSalt`. Attacker input: none needed beyond normal timing - relies on `SALT_TTL_MS = 5*60*1000` cache window. Preconditions: contract rotates `current_salt` mid-window (legitimate on-chain event, not attacker-controlled) while SDK cache is still 'valid' per `isCacheValid`. Call sequence: `sdk.intentBuilder().build()` uses stale cached salt to call `VersionedNonceBuilder.encodeNonce(staleSalt, deadline)`, signs via `IntentSignerNEP413.signIntent`, publishes; contract rejects with `INVALID_SALT`; SDK's retry logic (`withSaltRetry`) calls `SaltManager.refresh()` then rebuilds and resigns a second, differently-nonced `MultiPayload` for the same logical user intent and republishes it. Equality broken: SINGLE_EXECUTION - if the relayer had already accepted/broadcast the first payload before the rejection was observed by the SDK (race between publish result and retry trigger), both the stale-salt payload and the retried payload can end up executable, since they carry different nonces and neither invalidates the other. Scoped impact: Critical - a race between `INVALID_SALT` handling and relay acceptance can cause the same logical withdrawal to be signed and possibly executed twice, doubling the debit. Proof idea: vitest test mocking the relay to return success for the first publish attempt on a delayed response *after* the SDK has already triggered the retry due to a fast `INVALID_SALT`-looking condition, assert both signed payloads have different nonces yet correspond to the same underlying `IntentPrimitive[]`, and that the SDK never checks whether the first attempt actually landed before publishing the second.
