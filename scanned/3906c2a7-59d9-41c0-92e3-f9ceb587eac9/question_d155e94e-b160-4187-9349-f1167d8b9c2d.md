Target: `IntentSignerNEP413.signRaw`'s nonce handling: `nonce: Array.from(base64.decode(input.payload.nonce))`. Attacker input: a `payload.nonce` string that base64-decodes to a byte length other than 32 (e.g. a truncated or padded string forwarded from a malformed solver quote an integrator maps into a raw sign call). Preconditions: `signRaw` performs no length check on `input.payload.nonce` before decoding and hashing. Call sequence: integrator builds `Nep413RawPayload` with `payload.nonce = maliciousBase64` (decodes to, say, 16 bytes) and calls `signer.signRaw(...)`; `hashNEP413Message` hashes whatever byte array results; the SDK happily returns a fully signed `MultiPayloadNep413`. Equality broken: SIGNED == BUILT is nominally satisfied (whatever bytes were passed get signed), but the (nonce, verifying_contract) binding the Scope requires for single-contract-single-execution semantics is undermined because the SDK never enforces the 32-byte versioned-nonce shape that `decodeNonce`/`encodeNonce` assume elsewhere, meaning a signature can be produced and returned to the caller for a nonce shape the SDK's own invalidation/decoding logic (`decodeNonce`) cannot ever parse (`bytes.length !== 32` throws), permanently preventing that specific signed intent from ever being invalidated through the SDK's own invalidation path while still being independently publishable to the relay. Scoped impact: Critical - a signed, fund-moving payload exists that the SDK's own tooling cannot invalidate, and the user has no code path to prevent its later execution while believing invalidation succeeded (since invalidation code paths targeting other, well-formed nonces would silently no-op on this one due to the decode throw being caught/ignored upstream).
