### Title
Missing `return` after failed claim/session-write checks lets OIDC login succeed with an empty identity - ([File: core/sessions/oidcauth/oidc.go])

### Summary
`handleTokenExchange` in `core/sessions/oidcauth/oidc.go` checks the result of two security-relevant operations (extracting `email` from the verified ID-token claims, and persisting the OIDC session row) but, unlike every other error branch in this function, does not `return` when the check fails. Execution falls through and completes the login, exactly mirroring the reported bug class: a failure indicator is produced but ignored, and the caller proceeds as if the operation succeeded.

### Finding Description
`handleTokenExchange` is the callback endpoint reached by an unprivileged client completing an OIDC login flow (`POST` after the identity-provider redirect) [1](#0-0) . Every prior validation step in the function correctly logs an error, writes an error response, and `return`s — for bad JSON, bad state, failed token exchange, missing `id_token`, failed verification, and failed claims parsing [2](#0-1) .

Two checks break this pattern:

1. Email extraction:
```go
email, ok := claims["email"].(string)
if !ok {
    oi.lggr.Errorf("Failed to get email from claims. error: %v", err)
    c.String(http.StatusInternalServerError, "Failed to get email from claims")
}
```
There is no `return` here [3](#0-2) . If the IdP's ID-token claims lack a string `email` field, `ok` is `false`, `email` is the zero value `""`, an error body is written to the response — but the function keeps running.

2. Persisting the OIDC session:
```go
_, err = oi.ds.ExecContext(
    ctx,
    "INSERT INTO oidc_sessions (id, user_email, user_role, created_at) VALUES ($1, $2, $3, now())",
    clSession.ID, strings.ToLower(email), role,
)
if err != nil {
    oi.lggr.Errorf("unable to create new session in oidc_sessions table %v", err)
    c.String(http.StatusInternalServerError, "Error creating session")
}
```
Again no `return` [4](#0-3) . If the DB insert fails (e.g., duplicate/constraint error, connection hiccup), the code still proceeds to treat the login as successful.

Because neither branch returns, execution continues to:
- `oi.auditLogger.Audit(audit.AuthLoginSuccessNo2FA, ...)` logging a successful login even though the session row write may have failed [5](#0-4) 
- `ginSession.Set(webauth.SessionIDKey, clSession.ID)` and `ginSession.Save()`, which establishes the gin session cookie tied to `clSession.ID` regardless of whether that session ID was ever persisted server-side [6](#0-5) 
- The final `c.JSON(http.StatusOK, ExchangeTokenResponse{Success: true})`, which overrides/duplicates the earlier `c.String(...)` error write and reports success to the client [7](#0-6) 

This is the same root cause pattern as the reported `call()`/`delegatecall()` finding: a boolean/error signal that indicates failure is produced and even logged, but the calling code does not branch on it and continues as though the operation succeeded.

### Impact Explanation
The most severe outcome is issuing a session cookie (`clsession_id`) for a session ID that was never written to `oidc_sessions` when the DB insert fails. Downstream session-lookup code (`AuthorizedUserWithSession`/OIDC session lookup) is not visible in the indexed portion of this file, so it is uncertain whether an unwritten session ID would later fail to authorize, or — in some lookup implementations — be treated permissively. At minimum, this is a confirmed logic defect that:
- Falsely reports `Success: true` and audit-logs `AuthLoginSuccessNo2FA` for a login that the server itself flagged as failed.
- Can create a persisted `oidc_sessions` row with `user_email = ""` when the IdP omits/mistypes the `email` claim, silently associating a valid, cookie-backed session with an empty identity rather than rejecting the login as the code intends.

Because `IDClaimsToUserRole`/role mapping and the audit trail rely on `email`/claims that may be nonsensical in this path, this also risks cross-user/anonymous identity confusion in audit logs and any downstream logic keyed on `user_email`.

### Likelihood Explanation
Reachable by any unauthenticated client completing (or partially forging) the OIDC callback (`ExchangeToken` endpoint) once state validation passes — no privileged access is required. Triggering the missing-email branch requires control over, or a bug in, the identity provider's claims (a possible but not fully attacker-controlled condition, since it depends on the configured IdP). Triggering the DB-write-failure branch requires a transient DB error, which is lower likelihood but not attacker-controlled. Given the audit/branching rules restricting scope to unprivileged-actor-reachable authentication paths, this is included as a genuine, reachable authentication/session logic flaw, though full exploitability depends on code not present in the indexed context (the OIDC session-lookup/authorization path), which is unknown/unverified here.

### Recommendation
Add `return` immediately after both error-response writes:
```go
email, ok := claims["email"].(string)
if !ok {
    oi.lggr.Errorf("Failed to get email from claims")
    c.String(http.StatusInternalServerError, "Failed to get email from claims")
    return
}
...
_, err = oi.ds.ExecContext(ctx, "INSERT INTO oidc_sessions ...")
if err != nil {
    oi.lggr.Errorf("unable to create new session in oidc_sessions table %v", err)
    c.String(http.StatusInternalServerError, "Error creating session")
    return
}
```
This ensures the session cookie is never set and `Success: true` is never returned unless both the identity claim and the session persistence genuinely succeeded.

### Proof of Concept
1. Configure an OIDC provider (or a test double) that issues a valid, signature-verifiable ID token whose claims omit a string `email` field (e.g., `email` missing or non-string).
2. Complete the normal OIDC flow: `GET /sign-in` → redirect → provider callback → `POST` to the token-exchange endpoint with a valid `code` and matching `state`.
3. Observe that `handleTokenExchange` logs `"Failed to get email from claims"`, writes an interim `500` body, but does not return — it proceeds to create `clSession`, write `strings.ToLower("")` into `oidc_sessions.user_email`, set the session cookie via `ginSession.Save()`, and finally respond `200 {"success": true}`.
4. The client now holds a valid, cookie-authenticated session associated with an empty-email OIDC session row, despite the server-side log indicating the login should have failed.
(A second PoC path: make `oi.ds.ExecContext` fail, e.g. via a DB constraint/connection error, and observe the same fall-through to `Success: true` with a session cookie set for a `clSession.ID` never persisted in `oidc_sessions`.)
