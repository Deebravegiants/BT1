Target: tronAddressToHex (packages/internal-utils/src/utils/tronAddressToHex.ts) and its caller authHandleToIntentsUserId's 'tron' branch. Attacker input: a base58 string that decodes to exactly 21 bytes (version 0x41 + 20-byte hash) with no 4-byte checksum appended, versus the legitimate 25-byte checksummed Tron address for the same hash160. Preconditions: caller (integrator) passes a Tron address string obtained from an untrusted source into authHandleToIntentsUserId(identifier,'tron'). Call sequence: tronAddressToHex only requires payload.length >= 21 and payload[0] === 0x41, then hex.encode(payload.slice(0,21)) — it never validates or requires the checksum bytes; authHandleToIntentsUserId then does `0x${addressHex.substring(2)}`. Equality that breaks: the string signer_id claims to name == an account whose base58 form the true owner would recognize; here a caller can construct many different base58 strings (some checksum-mangled, all sharing the same 21-byte prefix but invalid overall) that all resolve to the same intents user id regardless of checksum validity, letting an attacker craft an address string that is not the canonical Tron address text but still authenticates as it. Scoped impact: High — a withdrawal/route configuration keyed off the base58 string chosen by the attacker could diverge from the canonical address text users expect while the derived signer identity stays valid, enabling confusion between the destination-address validation path and the signer-identity path. Proof idea: vitest test calling tronAddressToHex on a 21-byte (no checksum) base58 string and on the correctly checksummed 25-byte base58 string for the same hash160, asserting both return the same hex and that authHandleToIntentsUserId accepts the unchecksummed form without throwing.
