### Title
Unscoped `savedCallbacks` map keyed only by attacker-controlled `MessageID` allows cross-user response hijacking in the WebAPI trigger gateway handler - (File: `core/services/gateway/handlers/capabilities/handler.go`)

### Summary
### Finding Description
This is the analog of the FlywheelCore issue: a shared, mutable piece of state that custodies "value" for a specific caller (unclaimed rewards / a webhook response channel) can be overwritten by another actor, redirecting that value to the wrong party. In `FlywheelCore`, `flywheelRewards` custody was overwritten via `setBooster`. In the gateway's `WebAPIHandler`, the analogous shared custody structure is the `savedCallbacks` map, which stores the caller's HTTP `handlers.Callback` (the channel that eventually returns the workflow-run result to the requesting client) keyed only by the message's `MessageID`: [1](#0-0) [2](#0-1) 

`HandleLegacyUserMessage` unconditionally overwrites any existing entry in `h.savedCallbacks[msg.Body.MessageID]` with the new caller's callback — there is **no uniqueness/ownership check** before the assignment, unlike the newer v2 trigger handler, which explicitly rejects a request whose ID is already in flight: [3](#0-2) 

`MessageID` is attacker-controlled: it is a free-form string supplied in the incoming `api.MessageBody`, only constrained by length/format (`MessageIDMaxLen`, non-null-terminated) in `Message.Validate()`: [4](#0-3) 

When a node eventually responds with `MethodWebAPITrigger` for that `MessageID`, the gateway looks up whichever callback currently occupies that key and delivers the result to it, then deletes the entry: [5](#0-4) 

Because there is no per-sender scoping of the key (contrast with `core/services/gateway/handlers/common/requestcache.go`'s `globalID{sender, id}` composite key used elsewhere in the same package for exactly this purpose), any unprivileged client hitting the gateway's public WebAPI trigger endpoint can pick the same `MessageID` as another in-flight request. If attacker's request lands in the map after the victim's (a race that is easy to win by re-sending the same MessageID repeatedly while the victim's request is in flight), the victim's slot is silently overwritten, and:
- The victim's eventual node response is delivered to the attacker's callback (attacker receives another user's job-run output/response).
- The victim's original callback is orphaned and never gets a response (denial of the response, or a timeout instead).

This mirrors the `setBooster` rug vector's root cause: a single shared/global bucket of value (custodied response/callback) can be redirected by supplying attacker-chosen identifiers, with no ownership binding enforced at write time.

### Impact Explanation
This is a request-impersonation / cross-user response confusion. An unprivileged, unauthenticated party interacting with the gateway's public-facing webhook/trigger endpoint can receive a response payload intended for a different user's workflow trigger, and can deny the legitimate response to the original caller. Depending on what the trigger payload/response contains (workflow computation results, potentially business-sensitive data returned via `web_api_trigger`), this could leak data across tenants/users and disrupt availability of responses for victims. It does not directly move funds, but it is a concrete "cross-user response confusion" vulnerability class explicitly listed as acceptable in the validation criteria.

### Likelihood Explanation
Exploitability requires only: (1) knowledge that `MessageID` is attacker-supplied and unvalidated for uniqueness, and (2) winning a timing race by sending repeated requests with the same `MessageID` while the victim's is in flight (feasible via flooding, since callback lifetime is up to `CallbackMaxAgeSec`, default 120s). No special privileges, node access, or protocol trust are needed — this is directly reachable from an ordinary/unprivileged external client through the internet-facing gateway's legacy WebAPI trigger message path (`HandleLegacyUserMessage`). The fact that the newer v2 handler (`http_trigger_handler.go`) added an explicit duplicate-ID rejection strongly suggests this exact gap was recognized and fixed there but left present in the legacy handler.

### Recommendation
Scope `savedCallbacks` (and its key lookup) by both sender/caller identity and `MessageID` (e.g., the `globalID{sender, id}` pattern already used in `core/services/gateway/handlers/common/requestcache.go`), and/or reject/atomically fail requests whose `MessageID` is already in-flight, mirroring the check already present in `http_trigger_handler.go`'s `setupCallback`. Ensure the fix is applied to `HandleLegacyUserMessage` in `core/services/gateway/handlers/capabilities/handler.go`.

### Proof of Concept
1. Attacker sends a `web_api_trigger` legacy message to the gateway with `MessageID = "X"`.
2. Victim independently sends a `web_api_trigger` legacy message with the same `MessageID = "X"` (or attacker predicts/observes a victim's chosen ID and races it).
3. Both calls flow through `HandleLegacyUserMessage`; the second call's `h.savedCallbacks["X"] = &savedCallback{...}` (line 412) silently overwrites the first entry, with no check like the one in `http_trigger_handler.go` line 423-426.
4. When a DON node later responds for `MessageID = "X"` via `handleWebAPITriggerMessage` (line 148-161), the response is delivered to whichever callback is currently stored under `"X"` — potentially the attacker's — regardless of which caller's request actually produced that response.

Note: I was not able to fully trace the exact HTTP-layer code that constructs the incoming `api.Message`/`MessageID` from an end-user HTTP request before it reaches `HandleLegacyUserMessage` (i.e., confirming whether any upstream layer enforces per-session ID uniqueness) due to index/time constraints; if such enforcement exists upstream, it would need to be verified in a full codebase session to confirm end-to-end exploitability.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageID]
	delete(h.savedCallbacks, msg.Body.MessageID)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JSONRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}

func (h *httpTriggerHandler) setupCallback(ctx context.Context, requestID string, callback handlers.Callback, requestStartTime time.Time, workflowID string) (<-chan struct{}, error) {
	h.callbacksMu.Lock()
	defer h.callbacksMu.Unlock()

	if _, found := h.callbacks[requestID]; found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, fmt.Sprintf("requestID: %s has already been used. Ensure the requestID is unique for each request.", requestID), callback)
		return nil, fmt.Errorf("in-flight request ID: %s", requestID)
	}
