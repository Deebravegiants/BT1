### Title
Missing role-based access control on Bridge Show/Index endpoints exposes bridge `OutgoingToken` secrets to low-privilege authenticated users - (File: core/web/router.go)

### Summary
`SubQuery`'s incident stemmed from a state-mutating function (`setContractAddress()`) missing an `onlyOwner` modifier, letting any caller escalate privileges. In this codebase, the analogous bug class is missing role-based authorization on the bridge management HTTP endpoints: while `POST /v2/bridge_types` (`Create`) and `PATCH`/`DELETE /v2/bridge_types/:BridgeName` (`Update`/`Destroy`) are explicitly wrapped in `auth.RequiresEditRole`, the `GET /v2/bridge_types` (`Index`) and `GET /v2/bridge_types/:BridgeName` (`Show`) routes are registered with no role check at all beyond the generic session/token authenticator, so any authenticated user — including one holding only the `view` role — can read them.

### Finding Description
In `v2Routes`, all bridge write operations require the `edit` role: [1](#0-0) 

But the read routes for the same controller are left unguarded, protected only by generic session/token authentication (`authv2` group), which admits `view`-role users as well: [2](#0-1) 

`BridgeTypesController.Show` returns a full `BridgeResource`, including the bridge's `OutgoingToken`: [3](#0-2) 

`presenters.NewBridgeResource` unconditionally serializes `OutgoingToken` in JSON responses for both `Index` and `Show`, unlike `IncomingToken`, which is deliberately withheld except at creation time: [4](#0-3) 

This is a role/authorization gap analogous to the missing `onlyOwner` check in the SubQuery incident: a state-sensitive secret (`OutgoingToken`), which the design otherwise treats as privileged (write ops require `edit` role, and `IncomingToken` is redacted post-creation), is disclosed via a read endpoint accessible to any authenticated user regardless of role, including the lowest-privilege `view` role.

### Impact Explanation
A `view`-role user (the lowest privilege authenticated role in the RBAC model, verified by `RequiresEditRole`/`RequiresAdminRole` checks elsewhere in the same file) can enumerate and read every configured bridge's `OutgoingToken` via `GET /v2/bridge_types` or `GET /v2/bridge_types/:BridgeName`. This breaks the intended secret/role boundary that the rest of the bridge API enforces (write ops gated to `edit`), constituting unauthorized secret disclosure to an unprivileged actor — the same class of "should have been access-controlled but wasn't" bug as the SubQuery `setContractAddress()` case, just manifesting as read-path secret leakage instead of a write-path privilege takeover.

### Likelihood Explanation
High: exploitation requires only a valid low-privilege (`view`) API session/token, which is a normal, commonly-provisioned credential level in Chainlink node operations (e.g., read-only monitoring users). No special conditions or race are needed; a single authenticated `GET` request is sufficient.

### Recommendation
Wrap `bt.Index` and `bt.Show` with an appropriate role gate (at minimum `auth.RequiresEditRole`, consistent with the write operations on the same resource), or redact `OutgoingToken` from the `BridgeResource` presenter for non-privileged roles, mirroring how `IncomingToken` is already handled (`omitempty`, only populated on `Create`).

### Proof of Concept
1. Create a user with `UserRoleView` (e.g. via `POST /v2/users` as an admin, or use an existing view-role API token).
2. Authenticate as that user and issue `GET /v2/bridge_types` or `GET /v2/bridge_types/:BridgeName`.
3. Observe the JSON response includes `outgoingToken` for each bridge, despite the view-role user being blocked from `POST/PATCH/DELETE /v2/bridge_types*` by `auth.RequiresEditRole`.

// Show returns the details of a specific Bridge.
func (btc *BridgeTypesController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	name := c.Param("BridgeName")

	taskType, err := bridges.ParseBridgeName(name)
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	bt, err := btc.App.BridgeORM().FindBridge(ctx, taskType)
	if errors.Is(err, sql.ErrNoRows) {
		jsonAPIError(c, http.StatusNotFound, errors.New("bridge not found"))
		return
	}
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	jsonAPIResponse(c, presenters.NewBridgeResource(bt), "bridge")
}

type BridgeResource struct {
	JAID
	Name          string `json:"name"`
	URL           string `json:"url"`
	Confirmations uint32 `json:"confirmations"`
	// The IncomingToken is only provided when creating a Bridge
	IncomingToken          string       `json:"incomingToken,omitempty"`
	OutgoingToken          string       `json:"outgoingToken"`
	MinimumContractPayment *assets.Link `json:"minimumContractPayment"`
	UseConnectionManager   bool         `json:"useConnectionManager"`
	CreatedAt              time.Time    `json:"createdAt"`
}

// GetName implements the api2go EntityNamer interface
func (r BridgeResource) GetName() string {
	return "bridges"
}

// NewBridgeResource constructs a new BridgeResource
func NewBridgeResource(b bridges.BridgeType) *BridgeResource {
	return &BridgeResource{
		// Uses the name as the id...Should change this to the id

		URL:                    b.URL.String(),

		OutgoingToken:          b.OutgoingToken,
		MinimumContractPayment: b.MinimumContractPayment,
		UseConnectionManager:   b.UseConnectionManager,
		CreatedAt:              b.CreatedAt,
	}
