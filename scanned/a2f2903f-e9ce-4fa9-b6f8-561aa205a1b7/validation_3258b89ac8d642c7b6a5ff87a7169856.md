## Analysis: EIP-155 Replay Protection Gap in `pallet-revive`

The external zkSync report describes a scenario where the L2 system contract disables EIP-155 chain-binding for legacy transactions when `reserved[0] == 0`, enabling cross-chain replay attacks. Investigating polkadot-sdk's Ethereum-compatibility layer (`pallet-revive`), I found a directly analogous — and concretely reachable — issue.

### Title
Legacy (EIP-155-unprotected) Ethereum transactions are accepted by the on-chain runtime with no chain-ID binding, enabling cross-chain replay — (File: `substrate/frame/revive/src/evm/call.rs`)

### Summary
`pallet-revive`'s Ethereum-compatibility layer intentionally allows legacy transactions that omit the `chainId` field (to support "Nick's Method" deterministic deployments), but this exemption is enforced only informally by an optional, off-chain JSON-RPC gateway flag (`allow_unprotected_txs`, default `false`) rather than by the runtime's actual state-transition logic. The runtime function that decides whether to accept an Ethereum transaction as a dispatchable call unconditionally accepts any legacy transaction with no `chain_id`, regardless of the gateway configuration.

### Finding Description
In `substrate/frame/revive/src/evm/call.rs`, `GenericTransaction::into_call` performs the *only* chain-id validation for incoming Ethereum transactions: [1](#0-0) 

This explicitly special-cases legacy transactions with `chain_id == None`, letting them bypass the `ChainId` check entirely — a deliberate design choice documented in `prdoc/stable2512-1/pr_10476.prdoc` to support cross-chain deterministic contract deployment ("Nick's Method"). [2](#0-1) 

The decode/signature-recovery path for such a transaction (`TransactionLegacySigned::extract_recovery_id`) also has no chain-id requirement — the signature is valid with or without a chain id baked into `v`: [3](#0-2) 

Crucially, this on-chain acceptance path (`check_extrinsic` in `substrate/frame/revive/src/evm/runtime.rs`, which calls `into_call`) has **no dependency at all** on the `allow_unprotected_txs` flag: [4](#0-3) 

The `allow_unprotected_txs` restriction exists exclusively in the optional `eth-rpc` gateway binary's `send_raw_transaction` JSON-RPC handler, defaulting to blocking unprotected transactions: [5](#0-4) [6](#0-5) 

This means the "protection" is a **gateway-level UX guard**, not a **consensus-level rule**. Any path that reaches `check_extrinsic`/`into_call` without going through that specific gateway's `send_raw_transaction` method — e.g., submitting the SCALE-encoded `eth_transact` extrinsic directly via the node's standard `author_submitExtrinsic`, via a different eth-rpc instance run with `--allow-unprotected-txs`, via a differently-configured full node, or via any future/alternate frontend — will have the unprotected legacy transaction accepted and executed with full effect (value transfer, contract call, or contract creation).

### Impact Explanation
Because chain-id binding is entirely optional for legacy transactions at the runtime level, any historical Ethereum legacy transaction ever signed without EIP-155 protection (a category of transactions that is publicly known/broadcastable and not tied to any specific network) can be resubmitted as-is against any `pallet-revive`-based chain. If a user reuses the same Ethereum keypair/address across chains (a common practice, and one this pallet's `AddressMapper` explicitly supports by mapping the recovered `H160` to a fallback `AccountId`), and that address holds balance or has approved actions on the revive chain, an old signed transaction — never intended for this chain — can be replayed to move funds or invoke calls, exactly mirroring Scenario 1 of the referenced report (replaying a pre-EIP-155 transaction between networks to steal funds). It also allows any actor to bypass the specific gateway's opt-in safety flag by using an alternate submission path, undermining the very protection the flag is meant to provide.

### Likelihood Explanation
Likelihood is real but conditional: it requires (a) a victim account on the target `pallet-revive` chain that is address-linked to an Ethereum key which has ever produced/broadcast an unprotected legacy transaction (including deliberately-public "Nick's Method" style transactions, or genuinely old pre-2016 keys), and (b) the attacker being able to submit the extrinsic through any route other than the default-configured `eth-rpc` gateway (trivial for anyone with normal node/RPC access to a `pallet-revive` chain, since this is not a privileged action). No trusted-role compromise is needed — a normal unprivileged user or operator running a permissively-configured (or altogether different) frontend can trigger it.

### Recommendation
Move the chain-id/replay-protection enforcement from the optional `eth-rpc` gateway into the runtime's actual state-transition path (`GenericTransaction::into_call` in `substrate/frame/revive/src/evm/call.rs` and/or `check_extrinsic` in `substrate/frame/revive/src/evm/runtime.rs`), so the guarantee holds regardless of which frontend or submission path is used. If "Nick's Method" support must remain, restrict the exemption at the runtime level strictly to contract-creation calls (as the EIP-2470 pattern requires) rather than to all legacy calls, and consider gating it behind an explicit, chain-governed configuration rather than a client-side CLI flag that has no consensus-level effect.

### Proof of Concept
1. Construct a legacy RLP-encoded Ethereum transaction with `chain_id = None` (`v ∈ {27, 28}`), targeting an address/value transfer, signed by key `K`.
2. Ensure the corresponding `AccountId` (via `AddressMapper::to_fallback_account_id`) on the target `pallet-revive` chain holds funds/nonce matching the transaction.
3. Wrap the payload in the pallet's `eth_transact` call and submit it directly as a signed/unsigned extrinsic through any RPC path other than the gateway's `send_raw_transaction` (e.g., `author_submitExtrinsic`, or an `eth-rpc` instance started with `--allow-unprotected-txs`).
4. Observe that `into_call` (`substrate/frame/revive/src/evm/call.rs:82-94`) accepts the transaction with no chain binding, and the call executes — regardless of the target chain's identity or the gateway's default-safe configuration.

impl TransactionLegacySigned {
	/// Get the recovery ID from the signed transaction.
	/// See https://eips.ethereum.org/EIPS/eip-155
	fn extract_recovery_id(&self) -> Option<u8> {
		if let Some(chain_id) = self.transaction_legacy_unsigned.chain_id {
			// self.v - chain_id * 2 - 35
			let v: u64 = self.v.try_into().ok()?;
			let chain_id: u64 = chain_id.try_into().ok()?;
			let r = v.checked_sub(chain_id.checked_mul(2)?)?.checked_sub(35)?;
			r.try_into().ok()
		} else {
			self.v.try_into().ok()
		}
	}

		let hash = H256(keccak_256(&transaction.0));
		log::trace!(target: LOG_TARGET, "send_raw_transaction transaction: {transaction:?} ethereum_hash: {hash:?}");

		if !self.allow_unprotected_txs {
			let signed_transaction = TransactionSigned::decode(transaction.0.as_slice())
				.map_err(|err| {
					log::trace!(target: LOG_TARGET, "Transaction decoding failed. ethereum_hash: {hash:?}, error: {err:?}");
					EthRpcError::InvalidTransaction
				})?;

			let is_chain_id_provided = match signed_transaction {
				TransactionSigned::Transaction7702Signed(tx) => {
					tx.transaction_7702_unsigned.chain_id != U256::zero()

				TransactionSigned::Transaction4844Signed(tx) => {
					tx.transaction_4844_unsigned.chain_id != U256::zero()

					tx.transaction_2930_unsigned.chain_id != U256::zero()

					tx.transaction_legacy_unsigned.chain_id.is_some()
				},
