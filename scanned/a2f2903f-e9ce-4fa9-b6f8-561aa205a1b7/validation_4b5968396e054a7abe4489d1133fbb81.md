### Title
Inbound `ConcatenatedOpaqueVersionedXcm` handling creates spurious `OutboundChannelDetails` entries, consuming `MaxActiveOutboundChannels` capacity - (File: cumulus/pallets/xcmp-queue/src/lib.rs)

### Summary
`Pallet::handle_xcmp_messages` mutates `OutboundXcmpStatus` as a pure side effect of receiving an inbound page in `XcmpMessageFormat::ConcatenatedOpaqueVersionedXcm` format, inserting a new `OutboundChannelDetails` entry for the *sender* even though no outbound message is ever queued. This can consume slots in the bounded `OutboundXcmpStatus` vector (capacity `T::MaxActiveOutboundChannels`) and cause a subsequent legitimate `send_fragment`/`send_signal` call to fail with `Error::TooManyActiveOutboundChannels` / `MessageSendError::TooManyChannels`.

### Finding Description
In `handle_xcmp_messages`, for the `ConcatenatedOpaqueVersionedXcm` branch: [1](#0-0) 
the code unconditionally calls `Self::try_get_or_insert_outbound_channel(&mut all_channels, sender)` and writes the result back with `<OutboundXcmpStatus<T>>::put(all_channels)`. This happens purely because an inbound page arrived from `sender`, not because any outbound message is being sent to `sender`. `try_get_or_insert_outbound_channel` will `try_push` a brand-new `OutboundChannelDetails::new(sender)` into the bounded vec if one does not already exist: [2](#0-1) 
Every distinct `sender` ParaId that transmits at least one opaque-encoded page therefore occupies a slot of the bounded `OutboundXcmpStatus<T>` (capacity `T::MaxActiveOutboundChannels`): [3](#0-2) 
Elsewhere, when the runtime later needs to actually send something (`send_fragment`) or send a suspend/resume signal (`send_signal`), the same bounded vec is used and can fail with `TooManyChannels`/`TooManyActiveOutboundChannels` if full: [4](#0-3) [5](#0-4) 

However, there is an important mitigating mechanism: `XcmpMessageSource::take_outbound_messages`, which is invoked every block (by `cumulus-pallet-parachain-system` when building the collation), prunes any `OutboundChannelDetails` entry whose recipient has `ChannelStatus::Closed` (i.e., no real outbound HRMP channel exists to that ParaId): [6](#0-5) 
Since a spurious entry created purely by inbound-message processing has no corresponding real outbound HRMP channel (it was never opened by the victim toward the attacker's chain), `T::ChannelInfo::get_channel_status` will normally return `Closed` for that recipient, and the bogus entry is dropped the next time `take_outbound_messages` runs. Inbound XCMP message handling (via the `set_validation_data` inherent) executes before block finalization/collation collection, so the vulnerability window is confined to the current block: a legitimate outbound send attempted later in the same block (before finalization) can be blocked, but the spurious entries do not persist across blocks unless the attacker re-floods every block.

### Impact Explanation
Within a single block, an attacker who controls (or has caused the acceptance of) `T::MaxActiveOutboundChannels` distinct inbound HRMP channels to the victim parachain can send minimal `ConcatenatedOpaqueVersionedXcm` pages from each sender, filling `OutboundXcmpStatus` with placeholder entries before any legitimate outbound `send_xcm`/signal call executes in that block, causing that call to fail with `TooManyActiveOutboundChannels`/`TooManyChannels`. This is a genuine, code-confirmed griefing vector on the victim's outbound XCM capability, but it is transient per block rather than a permanent halt, because `take_outbound_messages` prunes closed-channel entries at the end of every block.

### Likelihood Explanation
Exploitation requires the attacker to control (or have accepted) enough distinct sibling parachains with actual, established inbound HRMP channels toward the victim — equal to `T::MaxActiveOutboundChannels` — since inbound XCMP messages are only deliverable over relay-chain-validated HRMP channels, not forgeable by an arbitrary signed account. Establishing that many one-way channels requires HRMP channel-opening deposits and (absent auto-accept configuration) acceptance by the victim/relay-chain HRMP process. This is realistic in the Cumulus threat model (malicious/compromised sibling parachains are explicitly considered, which is why suspend/backpressure mechanisms exist), but it is more costly and requires more setup than a single unprivileged extrinsic call, and the effect resets every block, requiring repeated flooding to sustain the DoS.

### Recommendation
Do not insert a new `OutboundChannelDetails` entry into `OutboundXcmpStatus` merely to record "recipient supports opaque encoding." Instead, only set the `notice_concatenated_opaque_versioned_xcm_support` flag on an existing entry (using `try_get_outbound_channel`, not `try_get_or_insert_outbound_channel`), or track this support flag in a separate, dedicated storage item (e.g., keyed `StorageMap<ParaId, OutboundChannelFlags>`) that is not bounded by `T::MaxActiveOutboundChannels` and is not conflated with the outbound-sending capacity accounting.

### Proof of Concept
Rust unit test in `cumulus/pallets/xcmp-queue/src/tests.rs` style:
1. Configure a mock with a small `MaxActiveOutboundChannels` (e.g. 2).
2. Call `Pallet::<Test>::handle_xcmp_messages` with an iterator yielding, for `MaxActiveOutboundChannels` distinct `ParaId`s, minimal pages encoded as `(XcmpMessageFormat::ConcatenatedOpaqueVersionedXcm, <empty or trivial opaque xcm>).encode()`.
3. Assert `OutboundXcmpStatus::<Test>::get().len() == MaxActiveOutboundChannels` even though no outbound message was ever sent to any of these ParaIds.
4. Within the same "block" (before calling `take_outbound_messages`), attempt `XcmpQueue::send_fragment` (or the `SendXcm` implementation) to a new, unrelated `ParaId` and assert it fails with `MessageSendError::TooManyChannels` / `Error::TooManyActiveOutboundChannels`.
5. Call `Pallet::<Test>::take_outbound_messages(...)` and assert the spurious entries are pruned (since `ChannelInfo::get_channel_status` for those ParaIds returns `Closed`), confirming the transient, per-block nature of the exhaustion.

		all_channels: &mut BoundedVec<OutboundChannelDetails, T::MaxActiveOutboundChannels>,
		recipient: ParaId,
	) -> Option<&mut OutboundChannelDetails> {
		for channel_idx in 0..all_channels.len() {
			if all_channels[channel_idx].recipient == recipient {
				return Some(&mut all_channels[channel_idx]);
			}
		}

		all_channels

			})
			.ok()?;
		all_channels.last_mut()
	}
