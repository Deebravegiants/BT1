### Title
`EngineMeter::charge_ref_time` never actually deducts fuel, allowing a contract to run extra Wasm instructions beyond its charged gas — (File: `substrate/frame/contracts/src/gas.rs`)

### Summary
`EngineMeter::charge_ref_time` computes the fuel amount that should be subtracted for weight consumed inside a host function, but discards the result of `checked_sub` instead of assigning it back to `self.fuel`. As a result, every time a contract calls a chargeable host function, the wasmi engine's fuel counter is restored to its pre-call value instead of being reduced by the host function's own weight cost, letting the contract execute additional real Wasm instructions "for free" relative to its `gas_limit`.

### Finding Description
The gas-syncing protocol between wasmi and `GasMeter<T>` works as follows, generated by the `#[define_env]` proc-macro in `substrate/frame/contracts/proc-macro/src/lib.rs` (`sync_gas_before`/`sync_gas_after`, lines 710–751): [1](#0-0) 

- On entering a host function, `sync_from_executor(fuel)` charges the wasm-instruction fuel spent since the last sync against `gas_left`, then the host function itself charges `RuntimeCosts::HostFn` (and possibly more) directly against `gas_left`.
- On leaving the host function, `sync_to_executor(before)` computes `ref_time_consumed` (the weight charged *during* the host function body) and calls `engine_meter.charge_ref_time(ref_time_consumed)`, whose return value is written back into wasmi via `__caller__.set_fuel(fuel)`.

The bug is in `EngineMeter::charge_ref_time`: [2](#0-1) 

```rust
fn charge_ref_time(&mut self, ref_time: u64) -> Result<Syncable, DispatchError> {
    let amount = ref_time
        .checked_div(T::Schedule::get().ref_time_by_fuel())
        .ok_or(Error::<T>::InvalidSchedule)?;

    self.fuel.checked_sub(amount).ok_or_else(|| Error::<T>::OutOfGas)?;
    Ok(Syncable(self.fuel))
}
```

`self.fuel.checked_sub(amount)` is only used for its `None`/`Some` discriminant (via `.ok_or_else(...)?`) to detect underflow; the `Some(value)` result — the correctly decremented fuel — is thrown away. `self.fuel` is never actually reduced, and `Syncable(self.fuel)` returns the *stale, pre-host-call* fuel value. This value is then written straight into wasmi's engine (`__caller__.set_fuel(fuel)` in the proc-macro-generated `sync_gas_after` block), effectively restoring the engine's Wasm-instruction fuel budget to what it was before the host call, ignoring the weight consumed by the host function body.

Because `GasMeter::gas_left` is still correctly decremented for the host-function cost (via the normal `charge()` calls), the pallet's own weight ledger stays internally consistent and eventually returns `OutOfGas`. However, wasmi's separate fuel counter — which is the mechanism that actually halts pure-Wasm-instruction execution via `Trap::OutOfFuel` — retains extra headroom equal to the host-function cost on every single chargeable host-function call. An attacker-controlled contract can repeatedly invoke cheap chargeable host functions (e.g., `seal_set_storage`, or any host function wrapped by the macro) to accumulate this un-deducted "banked" fuel in wasmi's counter, then spend it running additional real Wasm instructions in a tight loop before the discrepancy is finally caught (and only then as an `OutOfGas` abort) at the next `sync_from_executor` call.

### Impact Explanation
The scoped impact — "unauthorized extra Wasm execution steps beyond the charged gas limit" — is concrete: the actual CPU/instruction work the runtime performs for a contract call can exceed what `gas_limit` was supposed to authorize, because wasmi's fuel counter (the real-time execution throttle) is repeatedly topped up by the un-deducted host-function overhead on every host call. This is a weight/gas-metering bypass reachable purely through an attacker-authored contract making ordinary, permissionless calls — no privileged path is needed. While the transaction ultimately fails with `OutOfGas` once the ledger (`gas_left`) is checked again, the extra Wasm computation has already been performed by the node before that check triggers, i.e., real resource consumption exceeds the charged weight.

### Likelihood Explanation
Fully attacker-controlled and deterministic: any contract that calls chargeable host functions (essentially all interesting contracts) triggers `charge_ref_time` on every host-function exit. No races, reentrancy, or timing tricks are needed — the bug fires on every single sync-back regardless of fuel boundaries. The magnitude of "banked" fuel scales with the number of host-function calls made, which an attacker fully controls by writing a contract that loops calling a cheap host function many times before spending the accumulated slack in a pure-Wasm compute loop.

### Recommendation
Fix `EngineMeter::charge_ref_time` to actually assign the decremented value back to `self.fuel`:
```rust
fn charge_ref_time(&mut self, ref_time: u64) -> Result<Syncable, DispatchError> {
    let amount = ref_time
        .checked_div(T::Schedule::get().ref_time_by_fuel())
        .ok_or(Error::<T>::InvalidSchedule)?;

    self.fuel = self.fuel.checked_sub(amount).ok_or_else(|| Error::<T>::OutOfGas)?;
    Ok(Syncable(self.fuel))
}
```

### Proof of Concept
Rust unit test plan in `substrate/frame/contracts/src/gas.rs` tests module:
1. Construct a `GasMeter::<Test>::new(gas_limit)` with a known `ref_time_by_fuel`.
2. Call `sync_from_executor(engine_fuel_after_some_wasm_work)` to simulate entering a host function; capture returned `RefTimeLeft`.
3. Simulate host-function body cost by calling `gas_meter.charge(some_token)` directly (mirrors `charge_gas(HostFn)`).
4. Call `sync_to_executor(before)` and assert the returned `Syncable` fuel value equals `gas_left / ref_time_by_fuel` (i.e., properly reduced), not the stale pre-host-call fuel.
5. Assert: `engine_meter.fuel` (exposed via a `#[cfg(test)]` accessor or by checking the `Syncable` value) strictly decreases by `ref_time_consumed / ref_time_by_fuel` after each `sync_to_executor` call.
6. Integration-level fuzz test: deploy a fixture contract that loops calling a cheap chargeable host function N times then spins in a pure-Wasm busy loop; assert that total wasm-instruction fuel actually consumed (measured via wasmi instrumentation) never exceeds `gas_limit / ref_time_by_fuel`, and that execution halts with `OutOfGas` at or before that fuel budget is exhausted — currently it will exceed it by `N * hostfn_cost_in_fuel_units` before erroring.
