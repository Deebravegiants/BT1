## Title
Single global freshness/expiry parameter shared across all `OracleKey` price feeds in `pallet-oracle`'s `DefaultCombineData` - (File: `substrate/frame/honzon/oracle/src/default_combine_data.rs`)

### Summary
`pallet-oracle`'s default data-combination logic, `DefaultCombineData<T, MinimumCount, ExpiresIn, I>`, filters stale raw values using a single, pallet-wide `ExpiresIn` constant applied identically to every `OracleKey` (i.e., every price feed/currency pair) the pallet tracks. This is structurally the same flaw as the reported issue: one heartbeat/staleness window is used for multiple, heterogeneous feeds that in practice have very different natural update frequencies.

### Finding Description
`DefaultCombineData::combine_data` retains only raw values newer than `now - ExpiresIn` before aggregating: [1](#0-0) 

`ExpiresIn` is a single `Get<MomentOf<T, I>>` type parameter fixed at runtime-configuration time for the whole pallet instance, not per `OracleKey`: [2](#0-1) 

The pallet's `Config::OracleKey` is explicitly documented and used to represent multiple distinct feeds/currency pairs (e.g., the test suite feeds both `eur` and `jpy` keys through the same instance): [3](#0-2) [4](#0-3) 

The concrete kitchensink-runtime wiring confirms this: it instantiates one `pallet_oracle::DefaultCombineData<Self, ConstU32<5>, ConstU64<3600>>` for the entire pallet, applying a single 3600-second (1 hour) expiry to whatever set of `OracleKey`s (`u32`) operators feed: [5](#0-4) 

If a runtime uses this oracle to price multiple assets with genuinely different natural volatility/update cadences (e.g., a slow-moving stablecoin pair vs. a fast-moving volatile asset pair, analogous to USDC/USD vs ETH/USD in the referenced report), operators/governance are forced into the same trade-off called out in the finding: set `ExpiresIn` short enough for the fast asset (causing the slow asset's feed to appear "expired"/unusable more often than necessary, i.e., `get()`/`combined()` returning stale `prev_value` or `None`), or set it long enough for the slow asset (allowing the fast asset's price to be considered "fresh" and used by downstream consumers via `DataProvider`/`DataFeeder` even though it may be significantly stale relative to real market movement).

### Impact Explanation
Any pallet built on top of `pallet-oracle`'s `DataProvider`/`DataProviderExtended`/`DataFeeder` traits (e.g., a CDP/lending/PSM-style consumer, similar in spirit to `pallet_psm` seen wired in the same runtime) that reads `Pallet::get`/`get_value` for multiple asset keys inherits this shared staleness window. This can cause the consumer to use an out-of-date price for a volatile feed (mispricing, incorrect collateralization/liquidation decisions), or conversely to reject/discard valid recent data for a naturally slow-moving feed, degrading availability. This mirrors the original report's core impact: "either near constant downtime or insufficient staleness checks."

### Likelihood Explanation
This is a design/configuration-level issue rather than an attacker-triggerable exploit path — there is no unprivileged, attacker-controlled entry point that directly manipulates the expiry logic; the flaw manifests whenever a runtime integrator configures `pallet-oracle` with `DefaultCombineData` and feeds heterogeneous assets under one `ExpiresIn`. Likelihood of occurrence depends entirely on downstream runtime configuration choices, not on protocol-level attacker action against `pallet-oracle` itself.

### Recommendation
Parameterize freshness per `OracleKey` (e.g., a `Get`-like trait indexed by key, or a `Map<OracleKey, Moment>` configured by governance) instead of a single pallet-wide `ExpiresIn`, or document explicitly that runtime integrators using multiple heterogeneous feeds must implement a custom `CombineData` with per-key expiry rather than relying on `DefaultCombineData`.

### Proof of Concept
1. Configure a runtime with `pallet_oracle::Config::CombineData = DefaultCombineData<Runtime, MinimumCount, ConstU64<3600>>` (1-hour expiry) and two `OracleKey`s: `USDC_USD` (naturally updates ~every 24h) and `ETH_USD` (naturally updates ~every 1h), as in [5](#0-4) .
2. Feed `USDC_USD` once; without a re-feed within 3600s, `combine_data`'s `values.retain(|x| x.timestamp.saturating_add(expires_in) > now)` at [6](#0-5)  drops the value even though the underlying real-world price feed considers 24h fresh — `Pallet::get(&USDC_USD)` returns stale `prev_value` or `None`, causing consumer-side reverts/inability to act.
3. Alternatively, set `ExpiresIn` to 24h to accommodate `USDC_USD`; now a 20-hour-old `ETH_USD` value still passes the retain check and is aggregated into `Values`, and any consumer pallet calling `DataProvider::get(&ETH_USD)` receives a price that could be far from the current market price, causing mispriced collateral/PSM operations.
