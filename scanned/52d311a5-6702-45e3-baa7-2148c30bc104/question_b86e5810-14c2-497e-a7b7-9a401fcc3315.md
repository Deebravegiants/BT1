Target: `ShopifyAPI::Webhooks::Request#shop` (lib/shopify_api/webhooks/request.rb) reading the `x-shopify-shop-domain`/`shopify-shop-domain` header, consumed by `ShopifyAPI::Webhooks::Registry.process`. Attacker action: register a webhook on their own dev shop `attacker.myshopify.com`, capture a validly HMAC-signed webhook (raw body B, header `X-Shopify-Hmac-Sha256`=H computed by Shopify over B with the real `api_secret_key`), then POST the identical body B and H to the target app's webhook endpoint but with `X-Shopify-Shop-Domain: victim-shop.myshopify.com`. Preconditions: app uses `ShopifyAPI::Webhooks::Registry.process(request)` as documented, no extra shop check. Call sequence: `Request#to_signable_string` returns only `@raw_body`; `Utils::HmacValidator.validate(request)` recomputes HMAC over `@raw_body` only and ignores `shop`; `Registry.process` passes `request.shop` straight into `WebhookMetadata.new(shop: request.shop, ...)` without ever calling `ShopValidator.sanitize!`. Binding that breaks: `HMAC-signed bytes (raw_body) != bytes acted on (raw_body + shop header)`, so `shop authenticated by the signature != shop attributed to the handler`. Scoped impact: Critical - a forged webhook is accepted as belonging to `victim-shop.myshopify.com`, letting the attacker inject fabricated data into another merchant's webhook handler (cross-tenant). Proof idea: minitest + WebMock test building one `Request` with body/HMAC signed for shop A but header claiming shop B, asserting `HmacValidator.validate` returns true while `request.shop` differs from the shop that produced the signature.
