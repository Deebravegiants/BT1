Target: ShopifyAPI::Webhooks::Request#shop / #to_signable_string. Attacker action: attacker who has already registered their own webhook endpoint (per README) crafts an HTTP POST to their own endpoint including a genuine 'X-Shopify-Hmac-Sha256' computed over a chosen raw body, but sets header 'X-Shopify-Shop-Domain: victim-shop.myshopify.com' to a shop that never installed the app. Preconditions: app receives inbound webhook POSTs and calls Webhooks::Request.new(raw_body:, headers:) then Utils::HmacValidator.validate(request). Call sequence: Request.new normalizes headers -> shop reads 'shopify-shop-domain' header (unsigned) -> to_signable_string returns only @raw_body -> HmacValidator.validate computes HMAC over raw_body only, matches because the attacker owns a real installed shop and its real secret-derived hmac covers only body bytes they control. Binding: Request#shop (used to route/attribute the webhook to a tenant) must equal a value inside to_signable_string -- it does not, since to_signable_string == @raw_body only, never includes shop-domain header. Impact: Critical - cross-tenant data confusion: attacker's genuinely-signed webhook can claim to originate from an arbitrary victim shop domain, and any host app that trusts Request#shop for tenant attribution processes attacker-controlled webhook data under the victim's identity. Proof idea: minitest + WebMock constructing Webhooks::Request with raw_body signed under the attacker's own secret and a forged 'shopify-shop-domain' header set to a different shop, asserting HmacValidator.validate(request) returns true while request.shop reports the forged, unsigned shop value.
