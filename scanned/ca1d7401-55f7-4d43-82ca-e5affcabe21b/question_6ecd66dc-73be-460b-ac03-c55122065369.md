[File: packages/internal-utils/src/utils/stellarAddressToBytes.ts, function stellarAddressToBytes] stellarAddressToBytes verifies the base32 round-trip and the CRC16-XModem checksum but never checks that `payload[0]` (the version byte) equals the expected Stellar account-ID version byte (0x30/'G...'), so a string with a correct CRC but wrong version byte (e.g. a Stellar muxed-account or seed-type payload) still decodes successfully. Attacker input: a base32 string whose payload byte 0 is not 0x30 but whose CRC16 over that payload matches the trailing two bytes. Preconditions: this string is passed as userInfo.userAddress with userChainType:'stellar' into prepareSwapSignedData's 'STELLAR_SEP53' branch, which does `base58.encode(stellarAddressToBytes(userInfo.userAddress))` to build public_key. Call sequence: attacker supplies the wrong-version string as their own userAddress when calling publishIntent with a STELLAR_SEP53 signature; prepareSwapSignedData derives public_key from that string, not from verifying the SEP-53 signature. Equality broken: signer_id/public_key in the built payload == the account the attached signature actually proves control of, since the version byte encoding a specific key type (account vs. muxed vs. seed) is never validated. Impact: High, a signature bound to the wrong signer identity because public_key is derived from an unchecked address string rather than the signature. Proof idea: vitest test feeding stellarAddressToBytes a payload with version byte 0x00 (seed) but valid CRC and asserting it does not throw, then verifying prepareSwapSignedData accepts it as public_key.
