### Title
Unauthenticated NULL pointer dereference / node crash via missing `params` in `vault_publicKeyGet` gateway message - ([File: core/capabilities/vault/gw_handler.go])

### Summary
`GatewayHandler.HandleGatewayMessage` dispatches `vaulttypes.MethodPublicKeyGet` directly to `handlePublicKeyGet`, bypassing the `GatewayVaultRequestProcessor` pipeline that all other vault methods (`SecretsCreate`, `SecretsUpdate`, `SecretsDelete`, `SecretsList`) go through. That pipeline explicitly checks `req.Params == nil` before ever dereferencing it. `handlePublicKeyGet` has no such check and unconditionally dereferences `*req.Params`, causing a nil-pointer panic if a request arrives with `params` omitted/null — directly analogous to the Dovecot NOOP NULL pointer dereference from malformed parameters.

### Finding Description
In `HandleGatewayMessage`, methods are routed like this: [1](#0-0) 

For `MethodSecretsCreate/Update/Delete/List`, the request goes through `h.requestProcessor.ProcessRequest`, whose per-method handlers (`processCreateSecretsRequest`, `processUpdateSecretsRequest`, `processDeleteSecretsRequest`, `processListSecretIdentifiersRequest`) all guard against nil params before unmarshalling: [2](#0-1) [3](#0-2) 

But `MethodPublicKeyGet` is dispatched directly to `handlePublicKeyGet`, with no authorization step and no such guard: [4](#0-3)

If `req.Params` is `nil` (the natural, valid shape for a "get public key" call, which requires no input), `*req.Params` dereferences a nil `*json.RawMessage`, causing an immediate panic.

This handler is invoked from the node-side gateway connector's read loop, which reads JSON-RPC requests forwarded by the internet-facing Gateway and dispatches them to the registered handler with no `recover()`: [5](#0-4) 

Since `GetPublicKeyRequest` is intentionally unauthenticated (the vault master public key is meant to be publicly retrievable — no `AuthorizeRequest` call is made for this method, unlike the other vault methods), any unauthenticated actor able to reach the gateway can trigger this code path with a crafted request whose `params` field is omitted or `null`.

### Impact Explanation
A single unauthenticated JSON-RPC request (`method: "vault_publicKeyGet"`, no `params` field) forwarded through the gateway to a node's `GatewayHandler` causes an unrecovered nil-pointer panic in the read-loop goroutine. Depending on Go runtime panic propagation, this crashes the connector's read loop and can bring down the node process entirely — a remote, unauthenticated denial-of-service, directly matching the CVE's "malformed parameters → NULL pointer dereference → service crash" pattern.

### Likelihood Explanation
High: no authentication or authorization is required to reach `MethodPublicKeyGet`, and simply omitting or nulling the `params` field of an otherwise well-formed JSON-RPC envelope is trivial for any external caller who can submit gateway requests routed to this DON.

### Recommendation
Add a `req.Params == nil` guard in `handlePublicKeyGet` (mirroring the guards already present in `processCreateSecretsRequest`, `processUpdateSecretsRequest`, `processDeleteSecretsRequest`, and `processListSecretIdentifiersRequest`) before dereferencing `*req.Params`, returning a proper JSON-RPC error response instead of panicking. Additionally, consider wrapping `HandleGatewayMessage` dispatch in the connector read loop with a `recover()` to prevent any single malformed/unexpected handler panic from crashing the node process.

### Proof of Concept
1. As an unauthenticated client capable of reaching the gateway's forwarding path to a DON node (or directly crafting a message the connector's `readLoop` will dispatch), send a JSON-RPC request:
```json
{"jsonrpc":"2.0","id":"1","method":"vault_publicKeyGet"}
```
with the `params` field omitted (or explicitly `"params": null`).
2. `HandleGatewayMessage` routes this to `handlePublicKeyGet` without any nil check.
3. `json.Unmarshal(*req.Params, r)` dereferences a nil `*json.RawMessage`, panicking in the connector's `readLoop` goroutine, crashing the node process.
