### Title
Web API Trigger staleness check can be bypassed via signed-to-unsigned timestamp conversion - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
The Gateway's `WebAPIHandler.HandleLegacyUserMessage` validates message freshness by comparing an unsigned "now minus max-age" threshold against the client-supplied `payload.Timestamp`, which is cast from `int64` to `uint` without first checking its sign. Because Go integer conversion of a negative `int64` to `uint` wraps around to a huge value (two's-complement), an unprivileged sender can supply a negative timestamp and always pass the "stale message" check, regardless of the actual staleness rule the code intends to enforce. This mirrors the reported bug class: unsigned-integer arithmetic/conversion applied to a value that is not guaranteed to be non-negative, producing broken validation logic instead of the intended comparison.

### Finding Description
`handleLegacyUserMessage`'s freshness check is: [1](#0-0) 

```go
if payload.Timestamp == 0 { ... reject ... }

if uint(time.Now().Unix())-h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp) { //nolint:gosec // G115
    ... "stale message" ...
}
```

`payload.Timestamp` comes from `webapicap.TriggerRequestPayload`, which is decoded directly from the client-supplied, attacker-controlled JSON payload of an `api.Message` sent to the Gateway (`HandleLegacyUserMessage` is invoked from the unprivileged, internet-facing gateway message path). The only validation before this point is `payload.Timestamp == 0`; negative values are not rejected. `uint(payload.Timestamp)` for a negative `int64` wraps to a value close to `2^64`, which is virtually always larger than `uint(time.Now().Unix()) - h.config.MaxAllowedMessageAgeSec`. As a result the `>` comparison is false and the staleness check is silently skipped for any negative timestamp — the exact same class of defect as the audited report: an unsigned subtraction/comparison applied to values whose ordering assumption (here, "timestamp is non-negative and roughly `now`") is not enforced, breaking the intended validation instead of producing a revert.

### Impact Explanation
The staleness check exists to reject externally-submitted trigger messages whose claimed timestamp is too old (a basic anti-replay/anti-abuse control on the gateway's unprivileged message-ingestion path). By supplying a negative `Timestamp`, any unauthenticated/unprivileged client reaching the gateway's Web API Trigger handler can unconditionally bypass this freshness gate. This weakens the gateway's message-envelope validation and could allow acceptance/re-forwarding of otherwise-rejected (very old or arbitrarily aged) trigger payloads to DON nodes, undermining a control that is otherwise the only defense against stale/replayed trigger submissions at this layer. Impact is bounded to bypassing this specific freshness gate — it does not by itself grant authentication bypass, fund movement, or secret disclosure, so severity is best characterized as a validation/allowlist-adjacent bypass rather than critical.

### Likelihood Explanation
High likelihood of triggerability: any unprivileged actor able to send a message to the Gateway's web-api-trigger endpoint (as already exercised by `core/scripts/gateway/web_api_trigger/invoke_trigger.go`) can set `payload.Timestamp` to an arbitrary attacker-chosen value, including negative numbers, with no additional privilege required. The `//nolint:gosec // G115` comment shows this signed→unsigned conversion was a deliberate but incomplete suppression of the exact class of bug being flagged.

### Recommendation
Reject non-positive/implausible timestamps explicitly before the unsigned conversion, and perform the staleness comparison using signed arithmetic (or convert consistently after validating `payload.Timestamp > 0`), e.g.:
```go
if payload.Timestamp <= 0 {
    // reject as invalid
}
now := time.Now().Unix()
if now - int64(h.config.MaxAllowedMessageAgeSec) > payload.Timestamp {
    // reject as stale
}
```

### Proof of Concept
1. Craft a `web_api_trigger` `api.Message` with `TriggerRequestPayload.Timestamp` set to a negative value (e.g., `-1`), sign it, and submit it to the Gateway as any unprivileged sender, following the same flow as [2](#0-1) .
2. `HandleLegacyUserMessage` decodes the payload; `payload.Timestamp == 0` check passes (value is `-1`, not `0`).
3. `uint(payload.Timestamp)` wraps to `18446744073709551615`, which is always greater than `uint(time.Now().Unix()) - h.config.MaxAllowedMessageAgeSec`, so the "stale message" branch at [3](#0-2)  is never taken, and the message is forwarded to DON nodes as if it were fresh.
