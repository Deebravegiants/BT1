### Title
LDAP Bind with Empty/Unvalidated Password Enables Unauthenticated ("Passwordless") LDAP Bind Login - ([File: core/sessions/ldapauth/ldap.go])

### Summary
The `ldapAuthenticator.CreateSession` and `TestPassword` methods forward the client-supplied `SessionRequest.Password` directly into an LDAP `Bind` call with no check that the password is non-empty, mirroring the eZ Publish Legacy passwordless-login class of bug (GHSA-p9mp-vq4v-v5m5), where a login handler failed to properly verify credentials for LDAP-backed accounts.

### Finding Description
`CreateSession` builds a `searchBaseDN` from the attacker-supplied email and then calls `conn.Bind(searchBaseDN, sr.Password)` with the raw password from the unauthenticated `/sessions` HTTP endpoint, with no validation that `sr.Password` is non-empty: [1](#0-0) 

The same unvalidated pass-through happens in `TestPassword`, used by API-token creation/deletion flows: [2](#0-1) 

Per RFC 4513 §5.1.2, an LDAP "simple bind" with a non-empty DN and an *empty* password is defined as an **unauthenticated bind request**, which many LDAP server configurations will accept as successful ("bind succeeded") without actually validating any credential for that DN — precisely the "connect_but_fail" style class of bug that produced the original eZ Publish LDAP advisory (a login handler returning success for an unverified password). Nothing in `SessionRequest` (`core/sessions/session.go`, lines 16-22) or in the request-binding path enforces a minimum/non-empty password before it reaches `conn.Bind`. The public, unauthenticated route that accepts this payload is: [3](#0-2) 

If the configured LDAP server (or an intermediary proxy) honors RFC 4513 unauthenticated-bind semantics, an attacker who supplies any valid, known account email (email enumeration is trivial since usernames/emails are often not secret) together with an empty password string can cause `conn.Bind` to return `nil` (success), after which `FindUser` is used to fetch the user's real role and a full, roled `ldap_sessions` entry is created — granting a fully authenticated session cookie without ever supplying a valid password.

### Impact Explanation
If exploitable against the deployed LDAP backend, this is a full authentication bypass: an unprivileged/unauthenticated network client could obtain a valid session cookie with the target user's real role (potentially `admin`), enabling job creation/deletion, key management, and other privileged node-API actions — i.e., unauthorized access and potential fund-impacting job/run manipulation via the eZ Publish-class defect analog (CWE-285, improper authorization due to unverified password).

### Likelihood Explanation
Exploitability is entirely dependent on the specific LDAP server/directory's configuration (whether it accepts unauthenticated binds — many directories, e.g. some OpenLDAP/AD configurations, either reject binds with empty password by default or require `disallow bind_anon`/`EmptyPasswordDenied` type settings to block it). The code itself performs no defense-in-depth check, so the safety of this path relies entirely on external LDAP server hardening rather than the application. This mirrors exactly the "rare cases" caveat in the original eZ Publish advisory — it is dependent on backend behavior, but the application layer provides no compensating control.

### Recommendation
Add an explicit application-level guard in `ldapAuthenticator.CreateSession` and `TestPassword` (and any other LDAP bind call site) to reject empty (or whitespace-only) passwords before calling `conn.Bind`, e.g.:
```go
if sr.Password == "" {
    return "", errors.New("password is required")
}
```
This prevents reliance on external LDAP server semantics for unauthenticated-bind handling and closes the passwordless-login analog regardless of directory configuration.

### Proof of Concept
1. Identify or guess a valid user email registered in the configured LDAP directory (e.g., via `AdminUserGroupCN` role membership or general account enumeration).
2. Send an unauthenticated request to the node's public `/sessions` endpoint:
```
POST /sessions
Content-Type: application/json

{"email":"victim@example.com","password":""}
```
3. In `ldapAuthenticator.CreateSession`, `conn.Bind(searchBaseDN, "")` is invoked (core/sessions/ldapauth/ldap.go:408). If the backend LDAP server treats this as an RFC 4513 unauthenticated bind and returns success, `returnErr` remains `nil`, `FindUser` resolves the victim's role, and a new `ldap_sessions` row plus session cookie is issued for the victim account — without ever supplying a correct password.
