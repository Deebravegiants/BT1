### Title
Incomplete request-body secret redaction in the debug request logger allows disclosure of authentication secrets to logs - (File: core/web/router.go)

### Summary
The EasyFi loss stemmed from a single, unprotected credential (a mnemonic on an "official transfer" machine) that, once exposed, gave complete authority to move all protocol funds with no additional check. The reachable analog in this codebase is not a private-key compromise but a credential-*disclosure* vector on the node's internet-facing HTTP gateway: the request-body logging/redaction path in `core/web/router.go` only scrubs a hard-coded, shallow set of keys and only at the top level of the JSON body, so authentication-relevant fields sent by ordinary unprivileged API clients (e.g., API/session secrets, external-initiator/bridge tokens) can be written verbatim into the node's debug logs.

### Finding Description
`loggerFunc` wraps every HTTP request and unconditionally logs the parsed request body via `readBody` → `readSanitizedJSON`: [1](#0-0) 

`readSanitizedJSON` only inspects the **top-level** keys of the JSON object and redacts a key if it matches the `blacklist` map or contains the substring `"password"`: [2](#0-1) 

The blacklist itself is narrow:

```
var blacklist = map[string]struct{}{
    "password":             {},
    "newpassword":          {},
    "oldpassword":          {},
    "current_password":     {},
    "new_account_password": {},
}
```

This means any JSON field whose name does not contain "password" is logged in cleartext, and any field nested inside a sub-object or array is never inspected at all (the function does not recurse). Multiple authentication-relevant JSON fields used by unprivileged/less-privileged API consumers do not contain "password" and are therefore not redacted by this filter:

- `SessionRequest.WebAuthnData` (`webauthndata`) — WebAuthn assertion data submitted during login: [3](#0-2) 
- `ChangeAuthTokenRequest.Password` is caught (contains "password"), but the resulting `auth.Token{AccessKey, Secret}` returned/echoed in later API-token flows uses field name `secret`, not `password`: [4](#0-3) 
- External Initiator creation request/response echoes `incomingAccessKey`/`incomingSecret`/`outgoingToken`/`outgoingSecret` — none contain "password": [5](#0-4) , produced by [6](#0-5) 

Although `loggerFunc` only captures `c.Request.Body` (the *request*, not the response), several of these same field names are also valid **request** fields for subsequent calls (e.g., a client re-submitting a previously issued `secret`/`incomingSecret`/token as part of another request, or a bridge/external-initiator update flow), and none of them will be redacted because the filter is a hard-coded substring match on `"password"` only, applied to top-level keys.

This is a defense-in-depth/secret-hygiene gap analogous to EasyFi's root cause (an authentication secret escaping the narrow set of controls meant to protect it) — here the secret escapes the log-redaction control rather than a key-custody control.

### Impact Explanation
If Debug-level logging is enabled (a supported, documented node configuration) and log output is captured by any downstream system (file, syslog, log aggregator, or the optional `AUDIT_LOGGER_FORWARD_TO_URL` HTTP forwarder), authentication secrets submitted by ordinary API/session/external-initiator clients can be written to logs in cleartext. Anyone with read access to those logs (which is often a broader set of operators/support staff than those with API admin credentials) could reuse the captured secret to impersonate the session, external initiator, or bridge, i.e., authentication bypass via credential theft from an unintended channel. This does not require any code-execution bug — it is purely a logging/redaction gap on the internet-facing gateway.

### Likelihood Explanation
Requires: (1) Debug-level HTTP logging enabled on the node (a supported, non-default-but-documented configuration used for troubleshooting), and (2) an unprivileged/authenticated client submitting one of the non-"password" secret fields in a request body. Both conditions are plausible in real deployments (Debug logging is commonly turned on temporarily for diagnostics), and the vulnerable code path (`loggerFunc`) runs on every request through the node's public HTTP router, so the reachable surface is broad. However, exploitation additionally requires an attacker to gain access to the log stream/log destination, which is a secondary condition not controlled by the unprivileged client itself.

### Recommendation
Extend `isBlacklisted`/`readSanitizedJSON` to (a) recurse into nested objects and arrays, and (b) match on a broader set of substrings (`secret`, `token`, `accesskey`, `apikey`, `webauthn`, etc.) rather than only `"password"`, or switch to an explicit allow-list model for what may be logged from request bodies.

### Proof of Concept
1. Enable Debug-level web server logging on a Chainlink node.
2. As any unprivileged/authenticated API client, issue a request whose JSON body contains a field such as `{"secret": "<value>"}` (e.g., re-submitting an external-initiator or API token secret) to any `/v2/...` endpoint.
3. Observe the node's debug log line emitted by `loggerFunc`/`readBody`: the `secret` value appears in cleartext in the `"body"` field because `isBlacklisted("secret")` returns `false` (it does not match the blacklist and does not contain the substring `"password"`).
4. Anyone with access to the log destination (file/aggregator/forwarder configured via `AUDIT_LOGGER_FORWARD_TO_URL`) can read and reuse the disclosed secret.

	return func(c *gin.Context) {
		buf, err := io.ReadAll(c.Request.Body)

			// Implicitly relies on limits.RequestSizeLimiter

			// Functions as we would like, but horrible from an architecture

			}
			return

func readSanitizedJSON(buf *bytes.Buffer) (string, error) {
	var dst map[string]any
	err := json.Unmarshal(buf.Bytes(), &dst)
	if err != nil {
		return "", err
	}

	cleaned := map[string]any{}
	for k, v := range dst {
		if isBlacklisted(k) {
			cleaned[k] = "*REDACTED*"
			continue
		}
		cleaned[k] = v
	}

	b, err := json.Marshal(cleaned)
	if err != nil {
		return "", err
	}
	return string(b), err
}

func redact(values url.Values) string {
	cleaned := url.Values{}
	for k, v := range values {
		if isBlacklisted(k) {
			cleaned[k] = []string{"REDACTED"}
			continue
		}
		cleaned[k] = v
	}
	return cleaned.Encode()
}

// NOTE: keys must be in lowercase for case insensitive match
var blacklist = map[string]struct{}{
	"password":             {},
	"newpassword":          {},
	"oldpassword":          {},
	"current_password":     {},
	"new_account_password": {},
}

func isBlacklisted(k string) bool {
	lk := strings.ToLower(k)
	if _, ok := blacklist[lk]; ok || strings.Contains(lk, "password") {
		return true
	}
	return false
}
