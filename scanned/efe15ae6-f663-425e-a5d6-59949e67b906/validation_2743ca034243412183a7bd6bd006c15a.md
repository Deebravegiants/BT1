### Title
Unauthenticated pipeline run resume endpoint accepts attacker-controlled task result data - (File: core/web/pipeline_runs_controller.go)

### Summary
The Celo report describes an unprivileged/front-running actor being able to supply arbitrary `initCallData` to a proxy `deploy` call, letting attacker-controlled data flow into a `delegatecall`/initialization path that the rest of the system implicitly trusts. The closest reachable analog in this codebase is the `/v2/resume/:runID` endpoint, which is intentionally mounted on the **unauthenticated** router group and accepts a caller-supplied JSON body that is fed directly into a live pipeline run as the "result" of an async task — with the only gate being knowledge of a UUID.

### Finding Description
`v2Routes` registers the resume endpoint outside of the authenticated router group: [1](#0-0) 

`PipelineRunsController.Resume` parses the `runID` path parameter as a UUID, decodes an arbitrary JSON body into a `pipeline.ResumeRequest`, and passes the resulting `Result` straight into `App.ResumeJobV2` without any authentication, authorization, or ownership check tying the caller to that task: [2](#0-1) 

`ResumeJobV2` forwards the caller-supplied value directly to the pipeline runner: [3](#0-2) 

`ResumeRun` uses the value to update the task's stored result and, if that unblocks the pending task, restarts the pipeline run with that value baked in: [4](#0-3) 

The only "authentication" enforced is that the caller must know the random UUID assigned to the async task, which is generated when the `BridgeTask` is scheduled and embedded in the outgoing external adapter request's `responseURL`: [5](#0-4) 

This design mirrors the pattern in the Celo bug: a value provided by an untrusted party (`initCallData` there, the resume body's `Result` here) is trusted and consumed in a security-relevant execution path (a `delegatecall` there, a job/OCR pipeline result there) with no verification that the caller is the legitimate party that was supposed to supply it. The audit event name itself, `UnauthedRunResumed`, acknowledges this is a deliberately unauthenticated route: [6](#0-5) 

### Impact Explanation
If the per-task UUID is disclosed (e.g., via logs, a compromised/misbehaving external adapter, network capture of the outbound bridge request, or a race where an attacker observes/guesses IDs), an unauthenticated third party can:
- Inject arbitrary "price"/data values into a suspended pipeline run before it resumes, directly corrupting the observation feeding an OCR round or other job outcome.
- Trigger resumption of arbitrary runs at will, causing denial-of-service or corrupting downstream aggregation/consensus, without needing any node-level credentials.

This is analogous in severity to the Celo issue: an unprivileged party supplying attacker-controlled data into a trusted execution path, resulting in potential manipulation of oracle-provided results.

### Likelihood Explanation
Likelihood depends entirely on whether the UUID can be obtained by someone other than the intended external adapter. Since it is a `uuid.New()` v4 random value (128 bits of entropy) and is not exposed via any node API to unrelated users, brute-force guessing is impractical, and the design explicitly relies on the UUID as an unguessable bearer-token substitute for authentication. This is a known, intentional trust model in the code (as reflected by the `UnauthedRunResumed` audit event), rather than a newly discovered flaw. Exploitation therefore requires a separate disclosure vector (e.g., a compromised/malicious external adapter, third-party logging, or transport-level leakage) rather than being directly reachable from an unprivileged client with no other information — unlike the Celo bug, which required no secret knowledge to exploit.

### Recommendation
- Treat the resume UUID strictly as a bearer secret: avoid logging it, ensure it is only transmitted over the response URL to the specific bridge adapter, and consider rotating/limiting its validity window.
- Consider binding the resume operation to an additional shared secret or signature (e.g., HMAC keyed off a node-level secret) rather than relying solely on UUID unguessability, to defense-in-depth against future disclosure vectors.
- Add authorization/replay protections (e.g., single-use enforcement, expiry) around `/v2/resume/:runID` similar to protections applied elsewhere (e.g., the vault gateway's request digest/replay checks) so that even a disclosed UUID cannot be reused indefinitely to inject data.

### Proof of Concept
Not independently verified against a running node; based on static code review:
1. An external adapter is configured for an async bridge task; the node creates a pipeline run and sends the adapter a request containing `responseURL: http://<node>/v2/resume/<uuid>` (per `finalizeAndMarshalBridgeRequestData`).
2. If this UUID becomes known to a third party (e.g., via a compromised adapter or logged request), that party sends `PATCH /v2/resume/<uuid>` with an arbitrary JSON body (e.g., `{"data": "999999"}`) — no authentication headers required, since the route is registered under `unauthedv2`.
3. `PipelineRunsController.Resume` decodes the body and calls `App.ResumeJobV2`, which updates the task run result and resumes the pipeline with the attacker-supplied value, exactly as if the legitimate adapter had responded.

Uncertain/unverified: whether any additional out-of-band mitigation (e.g., network-level restrictions, WAF, or UUID exposure controls) exists in deployment configurations, since that is operational and not visible in this static review.

// Resume finishes a task and resumes the pipeline run.
// Example:
// "PATCH <application>/jobs/:ID/runs/:runID"
func (prc *PipelineRunsController) Resume(c *gin.Context) {
	taskID, err := uuid.Parse(c.Param("runID"))
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	rr := pipeline.ResumeRequest{}
	decoder := json.NewDecoder(c.Request.Body)
	err = errors.Wrap(decoder.Decode(&rr), "failed to unmarshal JSON body")
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}
	result, err := rr.ToResult()
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	if err := prc.App.ResumeJobV2(c.Request.Context(), taskID, result); err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	prc.App.GetAuditLogger().Audit(audit.UnauthedRunResumed, map[string]any{"runID": c.Param("runID")})
	c.Status(http.StatusOK)
}

func (r *runner) ResumeRun(ctx context.Context, taskID uuid.UUID, value any, err error) error {
	run, start, err := r.orm.UpdateTaskRunResult(ctx, taskID, Result{
		Value: value,
		Error: err,
	})
	if err != nil {
		return fmt.Errorf("failed to update task run result: %w", err)
	}

	// TODO: Should probably replace this with a listener to update events
	// which allows to pass in a transactionalised database to this function
	if start {
		// start the runner again
		go func() {
			ctx, cancel := r.chStop.NewCtx()
			defer cancel()
			if _, err := r.Run(ctx, &run, false, nil); err != nil {
				r.lggr.Errorw("Resume run failure", "err", err)
			}
			r.lggr.Debug("Resume run success")
		}()
	}
	return nil
}
