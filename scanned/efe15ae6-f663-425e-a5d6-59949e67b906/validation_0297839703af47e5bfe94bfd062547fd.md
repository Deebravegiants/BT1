### Title
Unauthenticated `/v2/resume/:runID` endpoint allows any caller to inject arbitrary task-run results into any pending pipeline task by guessing/enumerating task UUIDs - (File: core/web/pipeline_runs_controller.go)

### Summary
The node's HTTP API registers `PATCH /v2/resume/:runID` in the fully unauthenticated route group (`unauthedv2`), bypassing all of the session/token/role checks (`RequiresRunRole`, `RequiresEditRole`, `RequiresAdminRole`) that gate every other pipeline-mutating endpoint. `PipelineRunsController.Resume` parses the URL `runID` as a raw task UUID and an arbitrary JSON body as a `pipeline.ResumeRequest`, converts it to a `pipeline.Result` and calls `App.ResumeJobV2` directly, with no check that the caller is authorized to resume that specific task.

### Finding Description
`v2Routes` explicitly places `prc.Resume` in the unauthenticated group before the `authv2` group that wraps every other pipeline/job endpoint with `auth.Authenticate` + role checks: [3](#0-2) 

`Resume` itself performs no additional authorization — it only validates that `runID` parses as a UUID and that the JSON body decodes into a `ResumeRequest`, then forwards the caller-supplied `taskID` and `result` straight to `prc.App.ResumeJobV2`: [4](#0-3) 

This is structurally the same bug class as the MultiInvoker report: a privileged, state-mutating operation (`ResumeJobV2`, which unblocks a suspended pipeline task and injects attacker-chosen output/error values into it) is reachable by an unprivileged/unauthenticated caller who fully controls the identifying parameter (`taskID`) and the payload (`result`), with no validation tying the request to the entity that is supposed to be allowed to resume that task (e.g. the external adapter/bridge that originally suspended it). Any caller who can guess or observe a pending task's UUID (e.g. via logs, timing, or a previous legitimate resume URL) can inject arbitrary values/errors into that pipeline run, corrupting job outputs. The audit log entry (`audit.UnauthedRunResumed`) confirms this path is knowingly unauthenticated by design, but the report's bug class concern — no server-side validation that the caller is entitled to supply the specific input for the specific target — still applies.

### Impact Explanation
An attacker who obtains or guesses a suspended task's UUID can complete that pipeline task with arbitrary attacker-controlled values or errors, corrupting the job's output. For jobs whose outputs feed on-chain transactions or downstream financial decisions, this can lead to incorrect data being reported/acted upon, analogous to the loss-of-funds risk in the audit report where unvalidated user input let a caller force a withdrawal in someone else's favor.

### Likelihood Explanation
Likelihood is moderate: it requires knowledge of a pending task's UUID, which is a randomly-generated `uuid.UUID` not normally exposed to arbitrary users, so this is not directly exploitable without some leak of the UUID (e.g., from bridge callback URLs, logs, or webhook responses sent to external adapters). However, because the endpoint is intentionally unauthenticated (designed for external bridges/adapters to callback), any compromise or leak of that callback URL is sufficient — there is no secondary authentication factor.

### Recommendation
Bind resume authorization to the specific bridge/task rather than to "possession of the UUID" alone — e.g., require a per-task secret/HMAC token issued when the task was created and validate it in `Resume`, or scope resume tokens to the specific external adapter that suspended the task, so that knowledge of the `runID` alone is insufficient to inject a result.

### Proof of Concept
1. Attacker obtains a pending task's UUID (e.g. leaked via network logs, referrer headers, or a previous callback URL to an external adapter).
2. Attacker sends `PATCH /v2/resume/<taskID>` with a crafted JSON body matching `pipeline.ResumeRequest`, without any authentication headers.
3. `PipelineRunsController.Resume` accepts the request, decodes it, and calls `App.ResumeJobV2(ctx, taskID, result)`, completing the task with attacker-supplied data. [4](#0-3)

// Resume finishes a task and resumes the pipeline run.
// Example:
// "PATCH <application>/jobs/:ID/runs/:runID"
func (prc *PipelineRunsController) Resume(c *gin.Context) {
	taskID, err := uuid.Parse(c.Param("runID"))
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	rr := pipeline.ResumeRequest{}
	decoder := json.NewDecoder(c.Request.Body)
	err = errors.Wrap(decoder.Decode(&rr), "failed to unmarshal JSON body")
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}
	result, err := rr.ToResult()
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	if err := prc.App.ResumeJobV2(c.Request.Context(), taskID, result); err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	prc.App.GetAuditLogger().Audit(audit.UnauthedRunResumed, map[string]any{"runID": c.Param("runID")})
	c.Status(http.StatusOK)
}
